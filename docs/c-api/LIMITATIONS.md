# What the CNA C API does not do

This file is generated by `tools/c-api/generate_limitations.py` from the same in-memory
inventory that produces the compact [`COVERAGE.md`](COVERAGE.md) summary, plus the declared
non-symbol limitations in `tools/c-api/limitations.json`. It is not another inventory:
the full generated matrix records all 8,142 public C++
declarations and what became of each. This records only the ones that did **not** become a
callable C route, grouped by reason, so a consumer can decide whether one is relevant.

A limitation here is never an apology. Most of these are statements the canonical C++ makes
first -- a deleted operator, a protected hook, a template over a type C cannot name -- and
the C ABI is only repeating them.

## No C form: the reasons, by theme

Every unmapped symbol falls under one of these. The generator fails if one does not, which
is what stops this list from acquiring a silent "other" category.

### The inward direction of a two-way contract — 13 symbols

Some CNA surfaces come in pairs: one class a game calls, and a separate one the implementing module calls back with facts about the build. `GraphicsRendererSelection` and `GraphicsRendererSelectionAccessEXT` are the example, and the canonical header keeps them apart so the two directions are not confusable. The C ABI binds the outward half only: telling the selection which renderers are compiled in is a fact about the build, not a choice a caller may make.

### Hooks the platform layer calls into — 3 symbols

The platform layer hands input its window and its touch state through methods whose names say `INTERNAL_` out loud. A C caller owns no window handle and must not be able to re-point input at one; it reads input through the snapshot routes instead.

### The platform substrate the ABI is built on — 52 symbols

Interfaces a backend implements and the value types they exchange -- audio devices, recording devices, their formats. The C ABI is built ON this layer rather than exposing it: a C caller reaches the behaviour through the routes that use it, never through a C++ interface it would have to implement. The platform module itself is excluded from the inventory for the same reason (CBIND-047).

### Operations the C++ class deletes — 75 symbols

A deleted copy constructor or assignment operator has no behavior to expose. Its absence from the C ABI is the same statement the C++ class already makes.

### C++ iterators and range-for support — 68 symbols

An iterator has no fixed size, no stable representation and no C spelling. Every collection this ABI exposes is iterated as a count plus indexed access, or through an explicit enumerator handle where the canonical type has one.

### Protected members with no derived class to hang them on — 91 symbols

A protected member is mappable only when this ABI supplies a derived class that would override it. Where it does -- a game component's hooks -- the member is mapped; where the derived class is the caller's C++ code, there is nothing for C to override.

### Templates over an arbitrary C++ type — 42 symbols

C cannot name a C++ type, so a generic operation cannot be called from C at all. Where the canonical template has a small closed set of useful instantiations, the ABI names them one by one instead; the generic form itself stays unmapped.

### Values that are Sharp Runtime objects — 64 symbols

Sharp Runtime is an implementation dependency and never a C type. An operation whose value *is* such an object has nothing to hand across the boundary; see SHARP_RUNTIME_BOUNDARY.md.

### Friendship declarations — 38 symbols

A friend declaration grants a canonical CNA type access to another's internals. It declares no callable operation.

### Objects the caller never constructs or destroys — 22 symbols

Where CNA owns the only instance and its lifetime, the constructor and destructor are not operations a caller can perform, so they are not routes.

### C++ language mechanics with no runtime behavior — 75 symbols

Aliases, markers, move semantics, destructors and virtual type queries that exist for the C++ type system. C holds every object by handle, never deletes through an interface, and knows the type of everything it created, so it needs no query that stands in for `dynamic_cast`.

### Asynchronous-result objects nothing produces — 8 symbols

The canonical asynchronous pair completes before its Begin returns, so the C route is a single call that invokes the callback. The result object itself is never handed out.

### Canonical routes this ABI declines to bind — 5 symbols

A small number of canonical operations are unsafe or meaningless when reached through a C handle. Binding them would hand a caller a way to corrupt memory or to observe an event that can never fire; each is recorded individually in the generated full coverage matrix.

### `CNA::Internal` and `CNA::Graphics::detail` entry points declared in a public header — 8 symbols

The inventory excludes `CNA::Internal` and `Detail` by path, because those namespaces are how CNA's own modules talk to each other rather than surface an application uses. A few such entry points are declared in a public header for the compiler's convenience and reach the inventory that way. `ConfigureModelMaterialVariantsEXT` is the example: it is how the glTF importer installs a model's variant bindings, not an operation an application performs. What an application does with variants -- read the declared names, select one -- is bound on `CNA_ModelHandle` (CBIND-051D). The engine layer adds the same shape under its own `detail` namespace: `requireCapability`, `nameOfCapability` and `reportShaderCompileFailure` are the choke points its subsystems call, and a C caller sees their effect as a refusal or a log line rather than calling them. The questions they answer are already reachable -- `cna_graphics_device_supports_capability` for the capability, and each shader route's own validity reporting for the compile.

### Types the C ABI binds as a structure the caller owns — 4 symbols

Where the canonical type is a settings bag with no identity of its own, the C ABI binds it as a fixed-layout structure the caller stores and copies directly, rather than as a handle. The lifetime members of such a type -- its dispose, its destructor -- have nothing to do in C, because there is no handle to release and the caller's own storage ends the object's life. Adding a route for them would imply the structure holds something it does not.

### Build-time metadata and import policy — 39 symbols

These individually approved declarations describe intermediate serializers and source import policy, not runtime asset loading. Runtime content routes remain in scope.

### State managed by the network transport/session — 2 symbols

Guest and private-slot flags are transport/session bookkeeping. Owner Robert Vokac approved their no-C-form disposition on 2026-11-03; C callers use the existing getters.

## Limitations that are not about symbols

An inventory cannot record these, because they are properties of the package and the
promise rather than of any declaration.

| Subject | What it means | Status |
|---|---|---|
| **Enabled FFmpeg stays a system dependency** | `CNA_ENABLE_VIDEO=OFF` omits FFmpeg entirely while preserving the C video ABI with deterministic `CNA_RESULT_NOT_SUPPORTED` playback. When `AUTO/ON` selects video, libavcodec, libavformat, libavutil and libswresample come from the distribution rather than being copied into the package: copying them would take on their redistribution terms, freeze their soname against security updates and drag in their transitive libraries. | by design (CONSUMING.md) |
| **The static archive retains only unlocalizable GNU-unique C++ symbols** | A static CNA exports exactly the same `cna_*` names as the shared library: the whole closure is partially linked into one object and every other global symbol is localized. What cannot be localized is the set GCC emits as `STB_GNU_UNIQUE` -- function-local statics in inline and template code, whose uniqueness is what makes them correct. They are mangled C++ names, no C program can collide with them, and none is callable API. The build **fails** if a symbol of any other binding survives, so the exception cannot widen quietly. | by design (CONSUMING.md) |
| **One active CNA runtime per process** | A second `cna_game_create` while a game is alive returns `CNA_RESULT_INVALID_STATE`. This makes the interaction with CNA's process-level graphics and input state explicit; simultaneous runtimes are an ABI-semantic change requiring a reviewed design. | by design (HANDLES.md) |
| **Handles belong to their creation thread by default and never leave their process** | Using a handle from a thread other than its creator normally answers `CNA_RESULT_THREAD`. The two fire-and-forget `SoundEffect` play routes explicitly work from any thread, and a game may opt into queueing foreign-thread handle calls for service on the game thread with `cna_game_set_foreign_thread_calls_ext`; routes that must themselves drive or destroy the game still refuse off-thread use. Handles are not pointers, not serializable and not stable across processes. | by design (HANDLES.md) |
| **The ABI is 0.x and experimental** | An incompatible change requires only a minor-version increment, release notes and a regenerated baseline. The additive-only guarantee begins at 1.0, which is a separate, later decision. | by design (ABI_VERSIONING.md) |
| **The C smoke suite does not create a compiled Effect Framework effect** | `cna_effect_create_compiled`'s empty, malformed and MGFX refusals are renderer-independent and tested, but the C smoke supplies no valid XNA Effect Framework bytecode, so it never takes the accepting path even in a renderer build that supports compiled effects. That leaves `cna_effect_get_is_compiled_ext` proved there only on its `CNA_FALSE` branch, and clone-preserves-compiled-state asserted as a relationship between source and clone rather than on a genuinely compiled effect. A committed valid bytecode fixture exercised in a capable renderer build would close both. | not tested here (EFFECTS.md) |
| **C reflective enum fields are Int32-only** | The native `EnumTypeReader<T>` and reflective builder honor all eight legal .NET enum underlying types. The established C route `cna_reflective_type_reader_builder_add_enum_field` has no C++ enum type from which to infer that width and explicitly declares an `int32_t` field, so a C-authored reflective reader cannot currently describe a Byte-, SByte-, Int16-, UInt16-, UInt32-, Int64- or UInt64-backed enum. It refuses no valid Int32 use and no longer hides a native reader defect; adding a width argument would be a reviewed C ABI addition. | known limitation (content_readers.h) |

## Outside the header compatibility matrix

Taken from `tools/c-api/compatibility_matrix.json`, so the two cannot disagree. This
matrix proves source-level header compatibility; runtime and platform qualifications are
separate evidence:

- **Runtime and renderer behaviour.** This is a source-compatibility matrix for the public headers, not a runtime matrix. C API smoke, package, sanitizer, renderer and platform tests are registered in the applicable CMake configurations and carry their own evidence; this document does not claim that every smoke program runs under every renderer.
- **MinGW linking and execution.** The two MinGW rows cross-compile headers for a Windows target but do not link or run a Windows binary. Native Windows and Wine/DXVK runtime evidence belongs to their platform workflows, not to these header cells.
- **MSVC and Apple Clang.** Neither native compiler is a declared cell. Their platform builds and tests are useful independent evidence, but do not prove this matrix's per-header, per-language-mode contract.
- **Emscripten and Android NDK Clang.** Neither target compiler is a declared header cell. The separately built WebAssembly artifact and Android CNA builds do not imply that every public C header has been compiled alone in each language mode with those target macros and system headers.
- **C89.** The headers use `//` comments and mixed declarations, so C99 is the floor by design rather than by accident.
