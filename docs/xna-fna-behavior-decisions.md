# XNA/FNA behavior decisions

This is the permanent ledger for cases where measured Microsoft XNA 4.0 behavior differs from
FNA or from CNA's earlier FNA-derived behavior. It is not a defect list: current defects live only
in [`../handoff.md`](../handoff.md) §5.1.

FNA remains the normal readable implementation reference. When genuine XNA behavior has been
measured and disagrees with FNA, XNA wins. A new entry needs reproducible evidence, a regression
test, and the implementation disposition; source recollection or a stale consumer report is not
enough.

The first binding-led campaign was collected in 2026-09 from ten consumer repositories. Those
historical consumer findings do not establish any external binding's current release status.
The approved planning boundary here is CNA's native C API/C ABI; language-specific binding work
requires separate owner authorization. See [`binding.md`](binding.md).

Rows record accepted implementation decisions within their evidence's scope. A regression name
or commit does not prove every platform/input is covered or that its test ran in a particular
configuration. FNA comparisons in this review use local revision
`00498b0b81425b14bf8da23e68655215b9b5daa7`; runtime qualification remains with the subsystem
guides and their dated results.

## Deliberate retained boundaries

These are current decisions, not open defects:

- **`AddLocalGamer`'s local-gamer limit** (TQ-043). XNA's `AddLocalGamer` makes no local-gamer
  count check of its own (Net.dll IL_0000..00ee). The limit given at creation is the kernel's: 4
  for a gamer list, `BeginCreate` IL_000a..0016. Its refusal returns from the dispatch at
  IL_017d..0192 and passes through `NetworkSessionErrorHandler.ThrowExceptionFromResult` (Net.dll
  IL_0000..007f, which itself maps only `0x80040209`, `0x8004020A`, `0x8004020C`–`0x8004020E` and
  `0x80040214`), then
  `ErrorHandler.ThrowExceptionFromResult` (GamerServices.dll) and `Helpers.GetExceptionFromResult`
  (Framework.dll). No `KernelReturnCode` (Framework.dll) names a local-gamer limit, so the managed
  IL cannot show XNA's exception. CNA refuses synchronously with `InvalidOperationException`, as
  the kernel's dispatch result would be, after every check XNA makes and before anything is queued.
  C maps it to `CNA_RESULT_INVALID_STATE`. Tested by
  `NetworkSessionTest.AddLocalGamerChecksTheLocalLimitAfterEveryReferenceCheck`,
  `...AddLocalGamerThrowsAtMaxLimit` and `CApi_NetSmoke` (`validate_session_rosters`).
- **The last local gamer's leave ends the session** (TQ-043). A machine takes part in a session with
  1 to 4 local gamers (`GetLocalGamers` IL_0097..00dc refuses none). What XNA's kernel does when a
  machine's last local gamer leaves is not in managed IL. CNA's `RemoveGamer` (CNAEXT) raises that
  gamer's `GamerLeft` and then `SessionEnded` with the caller's reason. Tested by
  `NetworkSessionTest.RemovingTheLastLocalGamerRaisesGamerLeftThenSessionEnded`.
- **A SystemLink client whose host ends or removes it keeps its local gamers** (TQ-043). XNA reports
  the end as one `SessionStateChanged(Ended, reason)` (`ProcessStateChanged` IL_001e..0056).
  Whether the kernel also reports the machine's own gamers as leaving is not in managed IL. CNA
  raises `SessionEnded` alone and leaves the local gamers in the ended session, as an online
  session's end already did. Tested by
  `ENetBackendTest.AClientWithTwoLocalGamersEndsOnceWhenItsHostDisconnects`.
- **`NetworkSession.Dispose` empties the rosters and clears `Host`** (owner decision 2026-11-04,
  TQ-039). XNA's `Dispose(bool)` disposes every gamer of `AllGamers` and `PreviousGamers`
  (Microsoft.Xna.Framework.Net.dll `IL_00dd`–`IL_014b`) but leaves all four collections and `Host`
  as they were. CNA frees the gamers it owns at `Dispose`, so a kept pointer would dangle. It
  therefore empties `AllGamers`, `LocalGamers`, `RemoteGamers` and `PreviousGamers` and sets `Host`
  to null (`NetworkSession.cpp` `ReleaseSessionResources`). An `AddLocalGamer` that has not reached
  its `Update` is dropped. Tested by `NetworkSessionTest.DisposeClearsHostProperty` (a remote host
  and every roster), `DisposeClearsPreviousGamersSoNoDanglingPointerIsObservable` and
  `DisposeDropsAnAddedGamerThatHasNotJoined`.
- **SpriteEffect's MatrixTransform follows FNA, including M33 = -1** (owner decision 2026-11-04,
  TQ-035). XNA has no public SpriteEffect; its internal SpriteBatch matrix has M33 = +1
  (`SpriteBatch.SetRenderState` IL_0104-0188). CNA's public class is FNA's and is marked CNAEXT.
- **An EffectMaterial or base-Effect clone of a stock effect keeps the stock parameters and values but
  draws through the base Effect** (TQ-035 D9): XNA would draw it with the cloned stock shaders. Not
  changed by TQ-035.
- **A disposed OcclusionQuery's Begin/End throw `NullReferenceException`, not
  `ObjectDisposedException`** (owner decision 2026-11-04, TQ-035): the exact XNA failure, kept even
  though it contradicts CNA's general use-after-dispose rule; the C ABI reports it as
  `CNA_RESULT_INVALID_STATE`.
- **Unbinding a render target never ends its lost state** (owner decision 2026-11-04, TQ-035). XNA
  has one indirect exception: when a DiscardContents target with a depth or stencil buffer is unbound
  (or replaced) before anything was drawn into or cleared on it, `SetRenderTargets` IL_018a-0193 runs
  `ClearDirtyBuffers`, whose pending depth/stencil part goes through the public
  `Clear` (IL_00fe-0114) and so ends that outgoing target's lost state. CNA clears eagerly at binding and
  keeps no lazy-clear state, so it does not reproduce this; the owner's rule ("not on
  SetRenderTarget(s)") is followed as stated.
- **`GamePad.SetVibration` keeps clamping** (owner decision 2026-11-04, TQ-036). XNA multiplies each
  motor by 65535 and converts with `conv.i2` without a clamp (Microsoft.Xna.Framework.dll `SetVibration`
  IL_0000-0019); in C++ an out-of-range float-to-short conversion is undefined, so CNA forwards the float and
  the platform clamps it (NaN is off). `Sdl3EventMapperTests.GamepadMotorStrengthClampsAndTreatsNanAsOff`.
- **Stick quantization starts from CNA's normalized value.** A platform that already collapsed the native
  -32768 to -1 reaches the dead-zone rule as -32767; the TQ-036 tests qualify that normalized-domain
  contract, not every raw XInput sample.
- **A HiDef-built `.xnb` still loads on a Reach device** (owner decision 2026-11-04, TQ-033 D13). XNA refuses it: every graphics reader obtains its device through `GraphicsContentHelper.GraphicsDeviceFromContentReader` (Microsoft.Xna.Framework.Graphics.dll `IL_0054`–`IL_0090`). That call throws `ContentLoadException` unless `IsProfileCompatible(device, content)` holds (`IL_0000`–`IL_0022`: a Reach device takes Reach content only). CNA's header parser ignores the profile bit, flags `0x01`, which keeps existing content and the genuine HiDef fixtures, such as `platformer_hud/Hud.xnb`, loadable on a default Reach device. What a Reach device cannot create is still refused by the resource constructors themselves.
- **`AudioEngine::ContentVersion` stays 46** (owner decision 2026-11-04, TQ-022). XNA's field is the
  literal `0x27` (39) (Microsoft.Xna.Framework.Xact.dll, `.field public static literal int32
  ContentVersion`). CNA, FNA and the C ABI (`CNA_AUDIO_ENGINE_CONTENT_VERSION` in `xact.h`) publish
  46, the version CNA's XACT parser expects in `.xgs` and `.xsb` headers (`XactParser.cpp` warns on
  any other). `AudioEngineTest.ContentVersionIs46` pins it.
- **The `.xnb` header accepts more than XNA's** (owner decision 2026-11-04, TQ-018 O1). XNA's
  `ContentReader.PrepareStream` (Microsoft.Xna.Framework.dll `IL_0038`–`IL_0054`, `IL_0070`–`IL_0097`)
  takes only platform `'w'` and format version 5. CNA also accepts FNA's other fifteen platform
  identifiers and version 4 (`XnbAcceptedPlatforms`, `XnbHeader.hpp`), so content built for FNA,
  MonoGame and XNA's other platforms keeps loading. Its MonoGame LZ4 flag (`0x40`) is the same
  extension: XNA reads that bit as part of the graphics profile.
- **`Song` hashing and equality stay by file** (owner decision 2026-11-04, TQ-023) until native XNA is
  measured. XNA's `Song.GetHashCode` hashes `Name` (Microsoft.Xna.Framework.dll `IL_000f`–`IL_001b`),
  while its typed `Equals` asks the native `MediaItem_IsEqual` (`IL_002a`–`IL_003d`), whose rule the
  managed IL does not show. CNA compares and hashes the resolved file (`Song.cpp` `Equals`,
  `GetHashCode`); hashing the name alone would give two equal songs (same file, different labels)
  different hashes. A native identity probe (same file with different labels, different files with
  one label, `FromUri` aliases) settles it.
- **A positive collection or vertex-element count above CNA's limit is refused before allocating.** The limit is `XnbReadLimits.maxCollectionElementCount`, and the refusal is `ContentLoadException` (TQ-018, kept by TQ-033). XNA would attempt the allocation and fail with an out-of-memory error, or at the end of the stream. Negative counts follow XNA (Part 1).
- An `.xnb` external-reference cycle (an asset whose references lead back to itself) is refused with
  `ContentLoadException`, `Load<T>`'s documented refusal, on the first repeated read of an asset still
  being read (`ContentManager::XnbReadScope`, TQ-018). XNA and FNA recurse until the stack overflows:
  `ContentReader.ReadExternalReference<T>` (Microsoft.Xna.Framework.dll IL_0019-0033) calls `Load<T>`,
  which caches only after `ReadAsset<T>` (IL_0038, IL_0099, IL_00ac). A process crash is no contract a
  game relies on. Repeated references to an already loaded asset still come from the cache
  (`ContentExternalReferenceCycleTest`).
- Display modes report `SurfaceFormat::Color`. CNA's platform display value has no format and FNA
  makes the same explicit assumption. Change it only with genuine XNA evidence and a platform-level
  representation design.
- Native monitor handles are not exposed through the C ABI. The platform value is not necessarily
  an operating-system monitor handle, and the C boundary deliberately does not disclose native
  backend pointers.
- `GraphicsAdapter::Revision` and `SubSystemId` return documented zero values where FNA throws;
  CNA has no portable PCI identity source.
- `cna_camera_set_test_state_ext` accepts only states a handed-out test camera can really occupy.
  `CLOSED` and `NOT_SUPPORTED` remain refusal states, preserving read-after-write for every accepted
  state (BINDFIX-019).
- Launch-parameter key enumeration in C is deliberately sorted even though the native dictionary's
  enumeration order is a separate implementation detail.
