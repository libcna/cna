# Software <-> EasyGL XNA/Core parity ledger

This ledger is the durable evidence map for the parity campaign in
`plans/plan_software.md`. It was started on 2026-09-07 at CNA commit
`cde325ecd4d771d50b7d8ec3ef99f1657ad217ac` on branch `software`.

The behavioral authority order is measured Microsoft XNA 4.0/IL, FNA, EasyGL, current Software,
then prose. EasyGL is the CNA coverage reference, not permission to reproduce a demonstrated
EasyGL bug. A similarly named implementation method is not evidence. A test that succeeds by
recording an unsupported boundary is gap evidence, not parity evidence.

## Classification vocabulary

- `IN-SCOPE-XNA`: public XNA 4.0 behavior.
- `IN-SCOPE-CORE`: renderer-agnostic CNA plumbing required to make the XNA surface real.
- `DEFERRED-CNAEXT`: modern/CNAEXT behavior excluded from this campaign.
- `NOT-APPLICABLE-SOFTWARE`: physical GPU/window behavior with no meaningful CPU-renderer analog.
- `ALREADY-PARITY`: implementation and behavioral evidence already support the parity claim.
- `REAL-GAP`: in-scope behavior is absent, incomplete, silently degraded, or only boundary-tested.

The scope and verdict columns are intentionally separate: for example, a feature can be
`IN-SCOPE-XNA` and `REAL-GAP`, or `IN-SCOPE-XNA` and `ALREADY-PARITY`.

## Repository evidence census

- EasyGL owns 246 renderer example/test translation units. These include classic XNA behavior,
  renderer-native GL details, and modern CNAEXT shader/PBR examples; filenames are therefore an
  audit corpus, not an automatic scope list.
- Software owned 16 local example/test translation units and registered 60 `Software` CTests at the
  starting commit. The completed campaign registers 156 Software-labelled contracts, most from
  renderer-neutral graphics sources also compiled for EasyGL; all 156 pass under authenticated
  Xvfb with two-test concurrency.
- Later remediation tests already cover depth state, viewport/scissor, culling, wireframe, depth
  bias, exact indexed addressing, render-target readback/ordering/lifetime, blend equations/write
  masks, sampler component isolation, mip filters, texture/cube transfers and descriptor capacity.
- The RenderTargetCube fixtures that originally accepted Software's unsupported boundary now run
  the same positive face, mip, depth/stencil, MSAA, transfer and sampling contracts on Software and
  EasyGL after `SOFTWARE-119`.

### SOFTWARE-161: classic compiled XNA Effect assessment

This is a material classic-XNA gap. It is not `CNAEXT ShaderEffect`, and an opt-in dependency does
not change the API classification.

1. **Runtime representation.** `Effect(GraphicsDevice&, byte[])` accepts the original XNA/FNA
   Direct3D 9 Effect Framework binary emitted as `.fxb` or embedded by `EffectReader` in XNB. The
   public constructor validates that representation and distinctly rejects MonoGame MGFX.
2. **EasyGL representation.** EasyGL does not receive CNA source or a pretranslated CNA IR. Its
   runtime gives the original Effect Framework bytes to the pinned MojoShader effect parser; the
   OpenGL adapter translates the contained D3D9 vertex/pixel programs to GLSL 1.20, GLSL ES or
   GLSL ES 3 according to the active profile.
3. **Usable public APIs.** The shared graphics layer materializes `EffectParameter`, annotations,
   techniques, passes and current-technique selection from `ICompiledEffectRuntime`. Parameter
   writes, texture values, clone independence, pass state assignments and disposal are live under
   EasyGL rather than metadata-only facades.
4. **Executable evidence.** A clean `OPENGL33` build with
   `CNA_EASYGL_COMPILED_EFFECTS=ON` passes all 39 `EasyGLCompiledEffect*` tests on Mesa. The suite
   includes compiler-produced and authentic XNA 4 binaries, exact render-target pixels,
   ordinary/indexed/user/buffer draws, multi-stream input, instancing, pass/effect switches,
   2D/cube/volume samplers, targets and context recreation.
5. **SpriteBatch.** `SpriteBatch::Begin(..., Effect*)` applies every selected compiled pass and
   executes the supplied pixel shader while retaining the stock sprite vertex shader when the
   effect provides only a pixel stage. Shared tests cover custom output, multiple passes, slot 0,
   render-target sources and texture-run transitions.
6. **Models/content.** `EffectReader` reads the byte array from XNB and constructs the public
   Effect. `EffectMaterialReader` resolves an external effect, clones it and applies the parameter
   dictionary, including texture-valued parameters. Model shared resources assign those Effects
   to `ModelMeshPart`, so arbitrary compiled model materials can reach EasyGL's draw path.
7. **Instruction profiles.** MojoShader's translator covers classic D3D shader models through 3.
   Genuine compatibility therefore needs the register files, swizzles/modifiers, SM1 texture
   forms, SM2/3 arithmetic, predication/control flow, discard, derivatives/implicit LOD, VPOS,
   depth and MRT outputs used by valid XNA effect binaries—not merely the current small fixtures.
8. **Reusable parser/IR.** CNA already has reusable Effect Framework reflection/state translation
   around MojoShader. MojoShader exposes translated source/binary and reflection plus an evaluator
   for effect *preshaders*; it does not expose a CPU interpreter for the vertex and pixel shader
   programs. No existing CNA dependency supplies that missing executor.
9. **Reuse decision.** Software can reuse the effect parser, reflection descriptors, preshader
   evaluation and the original shader token buffers. It cannot obtain parity by invoking the GL
   adapter or the preshader evaluator. A Software-owned validated token IR is the smallest direct
   architecture; interpreting translated SPIR-V would add a second large subsystem and obscure
   D3D9-specific semantics.
10. **Minimum architecture.** Add an `ICompiledEffectRuntime` implementation that owns parsed
    programs and state; execute the vertex program against declaration-resolved multi-stream
    inputs; pass semantic outputs through the existing homogeneous clipper and perspective
    interpolator; execute pixels in 2x2 quads where derivatives are required; bind existing CPU
    2D/cube/volume surfaces and samplers; then publish COLOR0-3/depth/discard through existing
    MSAA, depth/stencil and blend stages.
11. **Estimated complexity.** This is a major standalone subsystem, estimated at roughly four to
    eight engineering weeks, 5-10 kLOC of interpreter/integration code, and a sizeable independent
    shader conformance corpus. Implementing only the current fixture opcodes would be a false
    capability claim.
12. **Useful phases.** SOFTWARE-162 builds the runtime and validated IR; SOFTWARE-163 implements
    vertex execution and draw-input integration; SOFTWARE-355 implements the independently testable
    texture-free triangle pixel/output slice; SOFTWARE-356 adds samplers, AddressW and texture
    instructions; SOFTWARE-357 closes MRT/target/SpriteBatch routing and SOFTWARE-358 closes classic
    line/wireframe routing under the SOFTWARE-164 umbrella; SOFTWARE-164/165 close the remaining SM1-3,
    content, lifecycle, stress and shared conformance before enabling the capability.
13. **Abstraction impact.** `ICompiledEffectRuntime` and the current draw token already provide the
    correct renderer-neutral boundary. The interpreter can remain reusable CPU-renderer code;
    common GraphicsDevice does not need shader opcodes or a GL-shaped API.
14. **Parity requirement.** Yes. EasyGL demonstrably executes this classic public Effect surface,
    SpriteBatch custom effects and content/model materials. Software advertises false and throws
    for the same valid bytes. Boundary tests are honest capability reporting, but they prove the
    gap rather than excuse it.

The current evidence therefore rules out final classification A. In addition to the Software-only
compiled-Effect executor gap, the audit has found a renderer-wide classic-XNA gap in the public
vertex texture/sampler collections. SOFTWARE-162/163/355/356/357/358/360 have completed bounded parser,
vertex, pixel, texture-sampler, MRT/target, SpriteBatch and line/wireframe phases, but the SOFTWARE-164/165 umbrellas remain pending;
SOFTWARE-168 is the separate shared binding task.
The final classification must account for both gaps after the remaining state/resource/default/skip
audit rather than describing compiled Effects as the only remaining defect.
