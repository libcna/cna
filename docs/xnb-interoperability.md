# `.xnb` interoperability: what CNA verifies, and what needs a real XNA runtime

`plans/plan_xnapipeline.md` `XNAP-026`.

A CNA-written `.xnb` file being readable by CNA is necessary but not sufficient: a reader and a
writer built together can agree with each other and still both be wrong about the format. This
document sets out the three gates CNA uses, which two of them run automatically, and exactly how
to run the third on a machine that has a real XNA 4.0 or MonoGame runtime.

---

## Gate 1 — CNA writes, CNA reads (automated)

Every supported type is written as a root asset and read back through CNA's own unmodified runtime
readers, and each asset writer is additionally decoded by the headless canonical decoder the
`.xnb` → CNB compatibility importer uses.

```bash
cmake --preset unit
cmake --build cmake-build-unit --target CnaContentTests
SDL_AUDIODRIVER=dummy ./cmake-build-unit/CnaContentTests --gtest_filter='Xnb*'
```

Necessary, cheap, and the fastest way to catch a regression. Not sufficient on its own.

## Gate 2 — an independent specification checker (automated)

`scripts/xnb_conformance.py` is a **second, separate implementation of the reader side**, written
in Python directly from the published Microsoft *XNA Game Studio 4.0 Compiled (XNB) Content
Format* specification. It shares no code, and no author's assumptions in code form, with CNA's C++
reader. It validates the container, the type-reader table, the object forms, and each supported
root's field layout, and it insists the root payload consume the body exactly.

```bash
python3 scripts/xnb_conformance.py path/to/asset.xnb
python3 scripts/xnb_conformance.py tests/assets/xnb/cna/windows/uncompressed/*.xnb
```

Its own trustworthiness is established the same way: it validates **every uncompressed real,
externally produced fixture in this repository** — MonoGame `Texture2D`, `TextureCube` with a full
DXT1 mip chain, `SpriteFont`, six `SoundEffect` wave formats, `Song`, and an XNA 4.0-produced
`List<String>` — before it is trusted to judge CNA's own output. It does not decode compressed
containers or `Model`, and says so rather than passing them.

This gate found a real reader bug that gate 1 could not: CNA's `SongReader` read a `Song`'s
duration as a bare `Int32` where the format writes `Object: Int32`. The real MonoGame fixture
decoded as 769282 ms instead of 3005 ms, left one byte of the file unread, and never dispatched to
the `Int32Reader` its own type table declared. See `plans/plan_xnapipeline.md` `XNAP-G6`.

It also settled how reader names must be spelled: real XNA content assembly-qualifies a reader
that does not live in `Microsoft.Xna.Framework` (so `Texture2DReader` carries
`Microsoft.Xna.Framework.Graphics, Version=4.0.0.0, …` and `StringReader` does not), because a
loading runtime resolves them with `Type.GetType()`, which searches only mscorlib and the calling
assembly. CNA writes the same spelling; see `XNAP-G7`.

## Gate 3 — a real XNA-compatible runtime (manual, off this machine)

**Not automated here, and not claimed.** No XNA 4.0, MonoGame or FNA runtime can be installed on
CNA's Linux CI host, and vendoring one as a test dependency is out of scope. What this repository
provides instead is everything that machine needs.

### The corpus

`tests/assets/xnb/cna/` holds CNA-produced `.xnb` files with per-file manifests recording the
producer, container description, root reader, size and SHA-256. Every source asset is CNA-original
and generated by the script below, so the corpus carries no third-party licence.

| Fixture | Type | What it proves |
|---|---|---|
| `texture_4x4.xnb` | `Texture2D` | Every texel is distinct and derived from its coordinates, so a runtime that transposes rows and columns or swaps channels renders a visibly wrong image rather than a plausible one |
| `texture_desktopgl_hidef.xnb` | `Texture2D` | The same asset with the DesktopGL platform byte and the HiDef profile flag |
| `sound_mono_22050.xnb` | `SoundEffect` | A 440 Hz 16-bit mono PCM tone: audibly correct or audibly wrong |

Regenerate after any writer change:

```bash
python3 scripts/generate_cna_xnb_fixtures.py --content-tool cmake-build-unit/cna-content
python3 scripts/xnb_conformance.py tests/assets/xnb/cna/windows/uncompressed/*.xnb
```

### The procedure

On a machine with XNA Game Studio 4.0 (Windows) or MonoGame:

1. Copy `tests/assets/xnb/cna/windows/uncompressed/*.xnb` into a project's `Content` output
   directory — **beside** the built `.exe`, not into the content project's source tree; these are
   already-compiled assets and must not be rebuilt.
2. Load them by name through the ordinary runtime API, with no custom readers registered:

   ```csharp
   var texture = Content.Load<Texture2D>("texture_4x4");
   var sound   = Content.Load<SoundEffect>("sound_mono_22050");
   ```

3. Check the observable result, not merely that loading did not throw:
   * `texture.Width == 4 && texture.Height == 4 && texture.Format == SurfaceFormat.Color`;
   * `GetData<Color>()` returns, for texel `(x, y)`, exactly
     `R = 16x + 1`, `G = 16y + 2`, `B = 16(x + y) + 3`, `A = 255`;
   * `sound.Duration` is about 200 ms and `sound.Play()` produces an audible 440 Hz tone.

4. Report the runtime, its version and the outcome in `plans/plan_xnapipeline.md`'s task log.

A failure here is a CNA bug regardless of what gates 1 and 2 say, and the file that failed should
become a regression fixture.

### The reverse direction

Externally produced `.xnb` files loading correctly in CNA is already covered by the read side and
its own fixture corpus — see
[`docs/xnb-content-pipeline-support.md`](xnb-content-pipeline-support.md). Both directions matter,
and they are tested independently.

---

## What is deliberately not a goal

**Byte-for-byte identity with XNA-produced files.** The format permits legal differences that
carry no meaning: type-table order (first-use order is as valid as any other), shared-resource
order, and whether a file is compressed. Two files that decode to the same object graph are
equally correct. The requirement is that an XNA-compatible reader interpret CNA's output
correctly, which is what gate 3 measures.

Where the format *does* fix an exact detail — the header layout, the 7-bit integer encoding, a
type's field order, an enum's numbering, the bone-reference width rule — CNA implements it exactly,
and gates 1 and 2 check it.
