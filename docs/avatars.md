# Avatars

CNA implements the XNA 4.0 avatar API (`AvatarDescription`, `AvatarAnimation`,
`AvatarRenderer`) with real behaviour on original CNA avatars. It is not an Xbox LIVE avatar
system: it neither reads nor produces Xbox avatar data or assets, and every avatar asset is
original CNA work generated by `tools/avatar_builder/`. CNA does not ship, use, extract, trace or
reference Microsoft's Xbox avatar models, textures, animations, marketplace items or artwork; it
aims at the classic console avatar's capability, proportions and feel with its own art. On Windows, XNA's avatar classes were stubs;
CNA implements the behaviour XNA's documentation describes for the Xbox 360 (never traced on a
console), with avatars that resemble that era in original art. What remains limited (baked shading, catalog edge cases,
likeness) is in [`gamer-services-known-limitations.md`](gamer-services-known-limitations.md).

**Who owns what.** The CNA service owns each account's `AvatarDescription` and its revision; the CNA
runtime owns the standard, immutable avatar catalogs (meshes, textures, animations), compiled into
every release. `AvatarDescription.BeginGetFromGamer` retrieves only the description, and
`AvatarRenderer` draws it with the locally installed catalog of exactly the version it names.
Normal rendering never downloads a per-user model or asset. The service's catalog packs are only an
optional, versioned update path for a catalog a client does not have (below).

## Descriptions

`AvatarDescription` keeps the XNA contract: an opaque buffer of exactly 1021 bytes, `IsValid`
true when the first byte is non-zero, `Height` in meters from the feet to the top of the head,
and `BodyType` (female or male; nothing else is added to the XNA enum). Inside the buffer CNA
stores its own versioned encoding. There are three formats; each keeps the bytes of the one
before and adds what it cannot express:

| Bytes | Field |
|---|---|
| 0 | format: 1, 2 or 3 -- non-zero, so XNA's `IsValid` rule holds |
| 1–3 | `C` `N` `A` |
| 4 | body type (0 female, 1 male) |
| 5–6 | height in millimeters, little endian (1450–2050) |
| 7 | build, 0 (slim) to 255 (heavy); 128 is the authored body |
| 8–9 | asset catalog version the item ids refer to: 3 (the baseline) or a later catalog; anything below 3 is not a CNA avatar |
| 10–30 | RGB colors: skin, hair, eyes, top, bottom, shoes, accessory |
| 31–42 | catalog item ids, 16-bit: hair, top, bottom, shoes, glasses, hat (0 = none, glasses and hat only) |
| 43–44 | format 2: facial-hair feature item id (0 = none) |
| 45–60 | format 2: face shape, one byte each, 128 = as authored: head width, head height, jaw width, chin size, cheek fullness, eye size, eye spacing, eye height, eye tilt, brow height, nose size, nose width, nose height, mouth width, mouth height, ear size |
| 61–62 | format 3: eyebrow style id (0 = the classic brows) |
| 63–64 | format 3: ear shape feature item id (0 = the first shape) |
| 65–76 | format 3: earrings, wristwear, gloves, rings: a 16-bit id and a side byte each (0 both, 1 left, 2 right; non-zero only when worn; gloves always 0) |
| 77–84 | format 3: makeup style ids: eye shadow, eyeliner, blush, lips (0 = none) |
| 85–99 | format 3: RGB colors: lips, eye shadow, blush, jewellery, gloves (black = unset: the palette's first) |
| 100 | format 3: proportions, 0 (compact: shorter legs, larger head) to 255 (long-limbed); 128 as authored |
| 101–116 | format 3: face shape 16–31, 128 = as authored: forehead height, cheekbone width, jaw taper, chin height, chin projection, brow spacing, brow angle, brow thickness, nose bridge, nose tip, upper lip, lower lip, ear height, ear angle, jaw angle, eye shape |
| up to 1016 | reserved, zero (from byte 43 in format 1, 61 in format 2, 117 in format 3) |
| 1017–1020 | CRC-32 (IEEE) of bytes 0–1016, little endian |

Every description is written, and read only, in the lowest format that says everything it says:
format 2 when it has facial hair or a shaped face, format 3 when it uses bytes 61–116 or names an
item the catalog marks `"format": 3` (everything catalog v3 revision 2 added; see Assets). So a
first-release avatar stays format 1 or 2, readable by every CNA build. A buffer that is not a CNA
description (an unknown format, a non-canonical one, a damaged checksum, non-zero reserved bytes)
keeps XNA's `IsValid` answer, which only looks at the first byte, but reports height 0 and the
female body type, and a renderer given it is `Unavailable`. CNA builds older than a format read it
that way; the service hands them a copy in a format they read instead (below).

`CreateRandom()` and `CreateRandom(bodyType)` produce valid descriptions from the newest catalog
compiled in, believable rather than any mix: a face from a curated preset with a little noise
(sometimes a compact figure), natural skin, hair and eye palettes with weights (fashion hair
colours rare), an outfit from the catalog or clothes in colours that go together, and accessories,
facial hair (by the catalog's per-body weights) and makeup (for anyone, more often on female
bodies) now and then, worn as people wear them. Passing a description's `Description` bytes to the
constructor reproduces the same avatar. The same generator with a seed is repeatable
(`AvatarCatalogContentTest.RandomAvatarsAreRepeatableVariedAndBelievable`).

## Descriptions from the service

`AvatarDescription.BeginGetFromGamer`/`EndGetFromGamer` read a gamer's avatar from the configured
CNA service (see `docs/gamer-services-server.md`): a signed-in gamer, a gamer returned by
`Gamer.GetFromGamertag`, or a remote `NetworkGamer` met in an online session all carry a service
identity. The operation completes during `GamerServicesDispatcher.Update` (never synchronously)
and `EndGetFromGamer` returns the stored description. A gamer without an avatar, without a service
identity (a remote System Link gamer), or an unreachable service yields an
invalid, all-zero description, so games take their usual "no avatar" path.
A signed-in local offline profile (no service configured, see `docs/gamer-services-server.md`) has
the avatar stored with the profile, created at random when the profile is, and the operation
completes synchronously with it. The service stores one
avatar per account and accepts only canonical CNA descriptions (formats 1 to 3) whose items exist
in a catalog it has imported; players change theirs with the CNA avatar editor (below) and
administration can assign one (`cna-gamer-services-admin <db> avatar <user> random`).

Games that share avatars in a session the XNA way (sending `Description` bytes to other machines
and constructing an `AvatarDescription` from them) need nothing from the service at all.

As in XNA, each signed-in player index keeps the description `EndGetFromGamer` returned for it
until that gamer's avatar changes; other gamers get a fresh description on every read.
`GamerServicesDispatcher.Update` reads a kept avatar again every 10 seconds (the service's copy, or
the local profile's store, which the CNA avatar editor writes) and, when it differs, empties the
slot and raises that description's `Changed` on the dispatcher thread with the `SignedInGamer` as
sender. The C++ description is a value, so its `Changed` is shared by every copy of it (subscribing
or unsubscribing through any copy is subscribing to the one event). An unchanged avatar, a new
catalog, or an unreachable service raises nothing; signing out empties the slot without an event.

## The avatar editor

The CNA avatar editor is a system screen of the Guide: **Edit avatar** on the Guide's Home opens it
over any game for a signed-in account or local profile, and `cna_avatar_editor` is the same screen
as a program of its own, as the console's editor was. No game contains customization code and no
XNA API is added for it. Opening it over a running game rather than leaving the game is CNA policy.

The avatar stands large on a lit stage, idle-animated (a wave on opening, a small gesture now and
then, a cheer on saving). Beside it a rail lists 21 categories in two groups, as the console's
editor grouped them:

- **Features**: Body, Skin, Face, Eyes, Eyebrows, Ears, Nose, Mouth, Hair, Facial hair, Makeup;
- **Style**: Outfits, Tops, Bottoms, Shoes, Headwear, Glasses, Earrings, Wristwear, Gloves, Rings.

Each category offers exactly what the catalog has, as rows of:

- **cards** rendered by the standard `AvatarRenderer` wearing that choice (styles, outfits, body
  type) and **named shapes** that set several features at once (59 catalog presets: face Round,
  Long, Square, Heart, Oval, Soft, Angular, Broad, Narrow, Youthful, Mature; eye, brow, ear, nose,
  mouth and body shapes; Balanced or Natural resets the category);
- **swatches** for skin, hair, eye, clothing, accessory, makeup, jewellery and glove colours;
- **sliders** for height (1.45-2.05 m), build, proportions and each of the 32 face features,
  labelled in words ("A little wide", "Very broad") rather than numbers;
- **chips** for the side an earring, watch or ring is worn on.

What the focus rests on is tried on at once; Accept keeps it, and leaving the row without it goes
back. A row says when a choice hides another ("Gloves hide rings"). The camera eases to what the
category is about -- the whole avatar, the head, a close face, a profile turned to show an ear,
the hands, the top, the bottoms, the shoes -- and the player turns it (right stick, Z/C, dragging)
and zooms (triggers, +/-, the wheel). Every category has a Reset button above its first row (Up
from the first row) that puts that category back as it was when editing started. X shuffles only
what the category shown covers; Y randomizes the whole avatar as `CreateRandom` does and keeps the
body type. Controller, keyboard and mouse reach every row.

It edits against the newest catalog the avatar's owner accepts -- the service's newest imported
catalog for an account (the one it validates a save against; a catalog this computer lacks is
installed as a pack first), the newest compiled-in one for a local profile -- and carries an older
catalog's avatar into it item by item. Saving is transactional: B asks to save, discard or keep
editing when anything changed; the service's `avatars.set` (one change per account every two
seconds) or the local profile store either holds the new avatar, or the editor explains why not and
keeps the edits. When the stored avatar changes elsewhere while the editor is open, an untouched
editor shows the new one and an edited one says that saving replaces it. Running games see a saved
avatar through `AvatarDescription.Changed`.

`cna_avatar_editor` is built with the examples (`CNA_BUILD_EXAMPLES`) whenever the default renderer
draws (not HEADLESS or STUB), as are `cna_avatar_review` and `cna_guide_review`.
`--capture DIR` walks the categories, tries on and keeps choices, randomizes and saves, writing a
PNG of each step; with `CNA_GAMER_SERVICES_AUTO_SIGN_IN` naming a profile and
`CNA_GAMER_SERVICES_PROFILES_DIR` a scratch store it runs unattended on a private display.

## Rendering

`AvatarRenderer` needs nothing beyond the XNA API. A game that creates a
`GraphicsDeviceManager`, adds a `GamerServicesComponent` (or calls
`GamerServicesDispatcher.Initialize`), and constructs a renderer from a description gets:

- **States.** A description without an avatar, or one CNA cannot read, is `Unavailable` and
  draws nothing. A valid one is `Loading` while one shared background thread assembles the body,
  wardrobe and face from the asset catalog, then `Ready`. Identical descriptions share the
  assembled model.
- **Bind pose and skeleton.** `ParentBones` is XNA's 71-entry table. Once ready, `BindPose`
  holds 71 local transforms relative to the parent, scaled to the description's height (bind
  rotations are identity, so they are pure translations).
- **Draw.** Every bone must be decomposable (`InvalidOperationException` otherwise). Each bone's
  rotation and scale are applied relative to its parent. The root also takes the supplied
  translation, and every other bone keeps the avatar's own bind offset, so one standard animation
  fits every height and build. Lighting is exactly `LightDirection`/`LightColor` plus
  `AmbientLightColor` (defaults 0.65 key and 0.35 ambient from the front). The face features are
  decals chosen by the `AvatarExpression` (left and right eyes and eyebrows independently). The
  model always renders solid, with clockwise front faces as in XNA, and the blend, depth,
  rasterizer and first sampler states are restored afterwards. There is no baked ambient occlusion
  or self-shadowing: a visual-quality limit, not a missing API (shadows a game draws itself, as in
  the XNA AvatarShadows sample, work).
- **Loading effect.** While loading, a renderer constructed with `useLoadingEffect` (the
  one-argument constructor's default) draws a softly pulsing translucent silhouette the height of
  the avatar. If loading completes during a `Draw` call, that call remains on the loading path and
  the next update observes `Ready` before the next draw consumes animation transforms.
- **Device.** The graphics device comes from the `IGraphicsDeviceService` of the service provider
  given to the dispatcher (XNA's rule); drawing before gamer services are initialized throws
  `InvalidOperationException`. A renderer's buffers and textures belong to that device: when it is
  disposed they are released with it, and a renderer drawn on a new device builds them again there.

## Animations

Each of the 31 `AvatarAnimationPreset` values is an original CNA clip on the 71-bone skeleton,
2.5 to 10 seconds long, with a keyed facial expression (idles blink). `BoneTransforms` holds 71
local animation deltas at `CurrentPosition`: non-root translations are zero, because the
renderer's `BindPose` supplies the joint offsets. Thus `BoneTransforms[i] * BindPose[i] *
parentWorld` computes the same joint as drawing that pose, including attachments. `Update` follows the reference exactly: negative time
plays backward, looping wraps by the remainder of `Length` (a position equal to `Length` is kept),
a non-looping animation clamps, and an overflowing step clamps to the nearer end. An undefined
preset value is a zero-length bind pose.

## Assets

All geometry, textures and motion are original CNA work generated by
`tools/avatar_builder/generate_avatar_catalog.py` (pure Python, deterministic, no downloaded or
third-party content).

**Catalog versions.** Catalog v3 is CNA's baseline avatar catalog: the oldest version CNA supports
and, today, the only one it ships. It lives in `modules/gamer-services/assets/avatars/v3/` and is
compiled into the library by `cmake/EmbedBinaryFiles.cmake` as `v3/<file>`. The versions a release
ships are listed in `CNA_AVATAR_CATALOG_VERSIONS` (`modules/gamer-services/CMakeLists.txt`), and
configuring fails on a catalog directory outside that list. Catalogs 1 and 2 were development
catalogs: they are not shipped and not supported, and Git history keeps them. A description,
manifest or catalog pack naming one is refused: the description decodes to nothing (height 0, a
renderer `Unavailable`), it is never drawn from catalog 3, and stale packs of them left on a
developer's disk are ignored.

**Revisions.** Catalog v3 was first released on 2026-09-30; revision 2 added entries, and
**revision 3** (manifest `"revision": 3`), the current content of the same version, reworks the
art of the same entries for visual quality. A revision may improve the art of
every item and add entries, but every first-release id keeps its kind and its description format
1 (hair 1–10, tops 20–28, bottoms 40–45, shoes 60–64, glasses 80–83, hats 100–104, facial hair
120–123), and everything a revision adds is marked `"format": 3`, so only a format 3 description
can name it. A first-release avatar is therefore still a valid, canonical description, and a CNA
build or service that reads only formats 1 and 2 never meets an id it does not have: the service
gives it a copy without the format 3 parts. A new catalog *version* (v4) was considered and set
aside: it would have doubled the shipped catalog and made v3 a second generation to support.
`AvatarCatalogTest.CatalogV3RevisionsKeepTheFirstReleaseAndAddOnlyFormat3Entries` pins the rule.

A description is drawn from exactly the catalog version it names — the compiled-in manifest of
that version, else an installed pack of it (below) — never from another. Files are found by size and SHA-256, so two
versions may use one file name for different contents and identical contents are shared. If a
later catalog the description names cannot be obtained at all, the baseline body is drawn with
every item replaced by its slot default (its ids are not read against another version). Preset
animations are system data, not part of a description, and come from the newest compiled-in
catalog.

Catalog v3 revision 3 has the entries revision 2 added, with their art reworked for visual
quality (the generator's modules say how each kind is built; `docs/avatar-art-direction.md` records
the visual language):

- a body per body type in stylized, friendly adult proportions of the console era (about 4.8
  heads tall): a head sculpted from a face profile, a back and a front outline, with the nose,
  eye sockets, brow, cheekbones, muzzle, lips and chin in its surface; sculpted ears (helix,
  bowl, antihelix, tragus, lobe); hands whose back widens to an arc of knuckles, with fingers that
  cascade when they curl; the face-feature decal patches; a proportion morph (byte 100) for
  compact to long-limbed figures at the same height;
- 143 wardrobe items and accessories fitted to both bodies, with labels, per-body CreateRandom
  weights and compatibility rules: 37 hairstyles (very short, buzzed, shaved and balding to long,
  curly, coiled, braided, tied back and ponytails), 28 tops, 17 bottoms, 14 shoes, 13 glasses,
  15 headwear, 6 earrings, 6 wristwear, 4 gloves and 3 rings;
- `featureItems`: 16 facial-hair styles (stubble to full beards) and 6 ear shapes;
- `faceStyles`, drawn from the face atlas rather than as models: 12 eyebrow styles (each with its
  own tile for every eyebrow expression; eyebrows take the hair colour), 4 eye shadow, 3
  eyeliner (with closed-eye tiles), 2 blush and 3 lip styles (one tile per mouth expression, an
  opacity each). Makeup is optional, for any body type, and tinted by its own colours;
- `faceControls` per body type: what each of the 32 face bytes does, as scale/move/rotate
  deformers with an ellipsoidal falloff on Head-weighted vertices, clamped to a stylized range;
  `facePresets`: the editor's 59 named shapes; `outfits`: 10 complete looks (Casual, Smart
  casual, Formal, Sport, Outdoor, Retro, Gamer, Summer, Winter, Cozy -- no branded or
  trademarked costumes);
- `faceAnchors` (where glasses and earrings ride) and `headSurface` (the head's radius by
  direction, used to fit hair under a hat);
- shared textures (`tex_*.png`: hair clumps, coils and twists, fabrics such as denim, knit, check,
  stripes, quilting and jersey, skin, and per-body stubble masks that hold both the grain and
  where the beard grows) named by materials and stored once;
- `face_features.png`, an atlas of every eye, eyebrow, mouth and makeup tile at 128 pixels per
  tile; `animations.glb` with the 31 presets as glTF cubic-spline rotation curves;
- `catalog.json`, listing every file (359 in all, 45.2 MB) with its SHA-256. Compiled in, the
  files are deflated (`cna_embed_binary_files ... COMPRESS`) to a 21.6 MB library
  (`cna_gamerservices_avatar_catalog`), inflated once when first used; only programs that use
  avatars link the catalog. (Revision 2 was 32.9 MB, 14.1 MB deflated: revision 3's hair, clothing
  and shoes are sculpted rather than lofted. Assembling an avatar from the compiled-in catalog took
  about 345 ms cold and 185 ms warm in a Debug build, against 235 and 110 ms for revision 2; an
  avatar already assembled is reused at once.)

**Compatibility rules are data**, not code: a hat's `hairCover` gives the line where its brim
meets the head and how far hair under it is lifted, and the assembly removes the hair the hat hides
and flattens the rest to the head surface under it (an open hat such as a visor has none);
glasses `follow` the eyes and earrings the ears, so face shapes move them with the feature;
`hides` lists kinds an item hides (gloves hide rings); items made of left and right parts mark
them (`cnaSide`) and are worn on the side the description names; stubble is drawn translucent
(`cnaBlend`).

Every GLB uses the same canonical 71-joint rig in XNA's exact topology: meters, Y up, facing +Z,
feet on y = 0, the avatar's left on +X. This is the **asset** space, not the standard API's
space: XNA avatars face -Z and their left is -X. `AvatarAnimation.BoneTransforms` and
`AvatarRenderer.BindPose` expose the half-turn about Y of the catalog transforms. The renderer
converts caller bones back to asset space for skinning and applies the half-turn before the
caller's `World`, so attachments computed from the public bones and bind pose agree with the
drawn body. The Guide editor and GPU art-review utility orient their own camera view accordingly.
Joints XNA leaves unnamed are helpers named `SlotNN`,
never skinned or animated. Materials are a base color factor, an embedded base-color PNG or a
shared catalog texture (`cnaTexture`; a near-white multiplier carrying shading and fabric detail)
and a description color tint (skin, hair, eyes, the three clothing colours, accessory, lips, eye
shadow, blush, jewellery, gloves). The reader refuses anything outside that contract: external
URIs, other rigs, non-identity bind rotations, out-of-range indices or weights, and oversized data.
Revision 2 needs contract level 2 (`CatalogReaderLevel`): the kinds, styles, rules and material
extras above. Every renderer draws it with the same two paths it already had (opaque parts, then
translucent decals); nothing in the catalog is renderer-specific.
`GamerServices_AvatarCatalogUpToDate` regenerates catalog v3 and compares it byte for byte (on a C library other than glibc, every
byte except catalog v3's six `FemaleShocked` arm rotations, which a non-convergent head solve froze
from glibc's libm and are checked structurally there; plans/plan_apple_m4.md AM4-166).
`AvatarCatalogTest.CatalogV3HasTheItemFeatureStyleAndAnimationContract` and
`V3DescriptionsAssembleExactlyAsRevised` pin the content; `AvatarCatalogContentTests` check every
model's geometry, every manifest reference and how accessories, makeup, ears and proportions
assemble; `TheBaselineCatalogV3IsTheOnlyCatalogThisReleaseShips` and
`DevelopmentCatalogsBelowTheBaselineAreNeverResolved` pin the version policy; and
`EmbeddedAssetsResolveByContentNotByName` and
`AnUnavailableCatalogNeverReadsItsIdsAgainstAnotherVersion` keep each version's files and ids its
own. `tools/avatar_builder/avatar_review.py` renders review sheets (views, faces, hair, wardrobe,
headwear, facial hair, accessories, makeup, animations, expressions) through the real renderer
(`cna_avatar_review`) and a CPU preview.

**Adding content.** New art is code in `tools/avatar_builder/` (`hair.py`, `garments.py`,
`accessories.py`, `face.py`, `catalog.py`). A new entry takes the next free id of its kind's
range, a label, random weights per body and `"format": 3`; regenerate with
`generate_avatar_catalog.py` (which also removes files it no longer writes), review the sheets,
and re-pin `V3DescriptionsAssembleExactlyAsRevised`. Changing a released entry's kind or format,
or removing an entry, is not allowed in a revision; the service refuses such a re-import.

### Catalogs a release does not have: catalog packs

The avatar model is the console's: the service owns each account's *description* (1,021 bytes and a
revision); the avatar *catalogs* are client content. A description on a catalog of this release
renders offline, and `BeginGetFromGamer` + `AvatarRenderer` transfer nothing but the description.
A pack is a whole immutable catalog version, installed once per client, never a per-user download.

When a description names a later catalog this build does not compile in, the renderer's loader
installs that exact catalog as one pack, if the configuration allows it (`avatarCatalogUpdates`, default on;
`CNA_AVATAR_CATALOG_UPDATES=0` turns it off; `maxAvatarCatalogBytes`, default 64 MiB):

1. `avatars.catalogPack` describes it: version, pack format, contract level (`reader`), description
   formats, the manifest's SHA-256 and size, and the total size. A pack this client cannot read or
   is not allowed to keep is refused before anything is downloaded.
2. The manifest and each file the client lacks are downloaded by hash from the service's file
   route; files this build compiles in (or another installed pack holds) are copied, not
   downloaded. Every file is verified into a staging directory.
3. The whole catalog is validated as the renderer will use it: every model against the 71-bone
   contract and bounds, every texture decoded, every item fitted to its body, the face atlas
   against its layout, all 31 animation presets.
4. One rename activates it. An interrupted install leaves only staging, which a retry reuses after
   verifying each file again; an invalid pack is discarded; nothing half-installed is ever read.

Installed packs are kept, not cached: `CNA_GAMER_SERVICES_CATALOGS_DIR`, else
`$XDG_DATA_HOME/cna/avatar-catalogs` (`%LOCALAPPDATA%\cna\avatar-catalogs` on Windows), one
self-contained `v<N>/` per version. Catalog versions are CNA-wide identities: the pack installed
first is that version, and a different catalog offered under the same number is refused. A version
that failed to install is not asked for again for a minute. A version below the baseline is never
installed, read from disk, listed as available or asked of the service.

The service negotiates what each client receives (`avatars.get` states the formats it reads, the
catalog contract level, the catalogs it has, whether and how large it installs packs). A client
that can draw the stored avatar, or will install its catalog, receives it; otherwise the service
sends a projection onto the newest catalog the client has, marked as such, and leaves the stored
avatar unchanged. A client that reads fewer description formats than the stored avatar uses (a CNA
build from before format 3) receives a canonical copy without what it cannot read: an item only
format 3 names becomes its slot's lowest older item, and eyebrows, ears, accessories and makeup are
left out. A manifest larger than one service message (revisions 2 and 3's are) is named by
`avatars.catalog` and read by hash from the file route. Games see an
ordinary description either way, and `AvatarDescription.Changed` follows the stored avatar's
revision, so installing a catalog or receiving a projection is never a change.

The fallback order for a description is: (1) its catalog is installed; (2) its pack is installed
now; (3) the service's projection (when it came from the service); (4) the deterministic default
avatar -- the newest installed body with the description's body type, height, build and colours,
every item its slot default (its ids are never read against another catalog); (5) `Unavailable`
only when not even a body can be drawn. Descriptions exchanged directly between games (bytes over a
`NetworkSession`) take (1), (2) and (4).
