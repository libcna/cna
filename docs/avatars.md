# Avatars

CNA implements the XNA 4.0 avatar API (`AvatarDescription`, `AvatarAnimation`,
`AvatarRenderer`) with real behaviour on original CNA avatars. It is not an Xbox LIVE avatar
system: it neither reads nor produces Xbox avatar data or assets, and every avatar asset is
original CNA work generated by `tools/avatar_builder/`.

## Descriptions

`AvatarDescription` keeps the XNA contract: an opaque buffer of exactly 1021 bytes, `IsValid`
true when the first byte is non-zero, `Height` in meters from the feet to the top of the head,
and `BodyType`. Inside the buffer CNA stores its own versioned encoding. Format 1 and format 2
share bytes 0–42; format 2 adds individuality format 1 cannot express:

| Bytes | Field |
|---|---|
| 0 | format: 1, or 2 when facial hair or a face shape is set — non-zero, so XNA's `IsValid` rule holds |
| 1–3 | `C` `N` `A` |
| 4 | body type (0 female, 1 male) |
| 5–6 | height in millimeters, little endian (1450–2050) |
| 7 | build, 0 (slim) to 255 (heavy); 128 is the authored body |
| 8–9 | asset catalog version the item ids refer to |
| 10–30 | RGB colors: skin, hair, eyes, top, bottom, shoes, accessory |
| 31–42 | catalog item ids, 16-bit: hair, top, bottom, shoes, glasses, hat (0 = none, accessories only) |
| 43–44 | format 2: facial-hair feature item id (0 = none) |
| 45–60 | format 2: face shape, one byte each, 128 = as authored: head width, head height, jaw width, chin size, cheek fullness, eye size, eye spacing, eye height, eye tilt, brow height, nose size, nose width, nose height, mouth width, mouth height, ear size |
| up to 1016 | reserved, zero (from byte 43 in format 1, from 61 in format 2) |
| 1017–1020 | CRC-32 (IEEE) of bytes 0–1016, little endian |

`CreateRandom()` and `CreateRandom(bodyType)` produce valid descriptions from the newest catalog
compiled in, with a random face and, for male bodies, sometimes facial hair; passing a
description's `Description` bytes to the constructor reproduces the same avatar. A description
that uses no format 2 field is written as format 1, which every CNA build reads. A buffer that is
not a CNA description (another format, a damaged checksum, non-zero reserved bytes) keeps XNA's
`IsValid` answer, which only looks at the first byte, but reports height 0 and the female body
type, and a renderer given it is `Unavailable`. CNA builds older than format 2 read format 2
descriptions that way; the service hands them a format 1 copy instead (below).

## Descriptions from the service

`AvatarDescription.BeginGetFromGamer`/`EndGetFromGamer` read a gamer's avatar from the configured
CNA service (see `docs/gamer-services-server.md`): a signed-in gamer, a gamer returned by
`Gamer.GetFromGamertag`, or a remote `NetworkGamer` met in an online session all carry a service
identity. The operation completes during `GamerServicesDispatcher.Update` (never synchronously)
and `EndGetFromGamer` returns the stored description. A gamer without an avatar, without a service
identity (a remote System Link gamer), or an unreachable service yields an
invalid, all-zero description, so games take their usual "no avatar" path.
A signed-in local offline profile (no service configured, see `docs/gamer-services-server.md`) has
the avatar stored with the profile, created at random when the profile is, and the operation
completes synchronously with it. The service stores one
avatar per account and accepts only CNA v1 descriptions whose items exist in a catalog it has
imported; administration assigns them (`cna-gamer-services-admin <db> avatar <user> random`).

Games that share avatars in a session the XNA way (sending `Description` bytes to other machines
and constructing an `AvatarDescription` from them) need nothing from the service at all.

As in XNA, each signed-in player index keeps the description `EndGetFromGamer` returned for it
until that gamer's avatar changes; other gamers get a fresh description on every read.
`GamerServicesDispatcher.Update` reads a kept avatar again every 10 seconds (the service's copy, or
the local profile's store, which the CNA avatar editor writes) and, when it differs, empties the
slot and raises that description's `Changed` on the dispatcher thread with the `SignedInGamer` as
sender. The C++ description is a value, so its `Changed` is shared by every copy of it (subscribing
or unsubscribing through any copy is subscribing to the one event). An unchanged avatar, a new
catalog, or an unreachable service raises nothing; signing out empties the slot without an event.

## Rendering

`AvatarRenderer` needs nothing beyond the XNA API. A game that creates a
`GraphicsDeviceManager`, adds a `GamerServicesComponent` (or calls
`GamerServicesDispatcher.Initialize`), and constructs a renderer from a description gets:

- **States.** A description without an avatar, or one CNA cannot read, is `Unavailable` and
  draws nothing. A valid one is `Loading` while one shared background thread assembles the body,
  wardrobe and face from the asset catalog, then `Ready`. Identical descriptions share the
  assembled model.
- **Bind pose and skeleton.** `ParentBones` is XNA's 71-entry table. Once ready, `BindPose`
  holds 71 local transforms relative to the parent, scaled to the description's height (bind
  rotations are identity, so they are pure translations).
- **Draw.** Every bone must be decomposable (`InvalidOperationException` otherwise). Each bone's
  rotation and scale are applied relative to its parent. The root also takes the supplied
  translation, and every other bone keeps the avatar's own bind offset, so one standard animation
  fits every height and build. Lighting is exactly `LightDirection`/`LightColor` plus
  `AmbientLightColor` (defaults 0.65 key and 0.35 ambient from the front). The face features are
  decals chosen by the `AvatarExpression` (left and right eyes and eyebrows independently). The
  model always renders solid, with clockwise front faces as in XNA, and the blend, depth,
  rasterizer and first sampler states are restored afterwards.
- **Loading effect.** While loading, a renderer constructed with `useLoadingEffect` (the
  one-argument constructor's default) draws a softly pulsing translucent silhouette the height of
  the avatar.
- **Device.** The graphics device comes from the `IGraphicsDeviceService` of the service provider
  given to the dispatcher (XNA's rule); drawing before gamer services are initialized throws
  `InvalidOperationException`.

## Animations

Each of the 31 `AvatarAnimationPreset` values is an original CNA clip on the 71-bone skeleton,
2.5 to 10 seconds long, with a keyed facial expression (idles blink). `BoneTransforms` holds 71
local transforms at `CurrentPosition`. `Update` follows the reference exactly: negative time
plays backward, looping wraps by the remainder of `Length` (a position equal to `Length` is kept),
a non-looping animation clamps, and an overflowing step clamps to the nearer end. An undefined
preset value is a zero-length bind pose.

## Assets

All geometry, textures and motion are original CNA work generated by
`tools/avatar_builder/generate_avatar_catalog.py` (pure Python, deterministic, no downloaded or
third-party content). Every catalog version lives in its own directory,
`modules/gamer-services/assets/avatars/v<N>/`, and all of them are compiled into the library by
`cmake/EmbedBinaryFiles.cmake` as `v<N>/<file>`. A released catalog never changes: catalog v1 is
frozen data (the generator that wrote it is in Git history), and the generator now writes v2.

A description is drawn from exactly the catalog version it names — the compiled-in manifest of
that version, else the service's — never from another. Files are found by size and SHA-256, so two
versions may use one file name for different contents and identical contents are shared. If the
named catalog cannot be obtained at all, the newest compiled-in body is drawn with every item
replaced by its slot default (its ids are not read against another version). Preset animations
are system data, not part of a description, and come from the newest compiled-in catalog.

Catalog v2 has:

- a body per body type: a large rounded head with a sculpted face shape, button nose and ears,
  single-surface arms and legs, sculpted hands, and the face-feature decal patches;
- 39 wardrobe items fitted to both bodies: 10 hair styles, 9 tops, 6 bottoms, 5 shoes, 4 glasses and
  5 hats (catalog v1's 18 ids in their v2 form, plus new ones), with per-body CreateRandom weights;
- `featureItems`: 4 facial-hair styles a format 2 description can name;
- `faceControls` per body type: what each face-shape byte does, as scale/move/rotate deformers
  with an ellipsoidal falloff on Head-weighted vertices — the face-only ones move the head, face
  decals and facial hair, the whole-head ones (width, height) also hair, hats and glasses;
- for every hair style, `hatAssets`: the style with what a hat hides removed and the rest
  flattened under one shared hat envelope, used whenever the hat item `coversHair`;
- `face_features.png`, an atlas of every eye (with a separate iris layer tinted by the eye color),
  eyebrow and mouth state at 128 pixels per tile; lips are translucent so they suit any skin tone;
- `animations.glb` with the 31 presets as glTF cubic-spline rotation curves;
- `catalog.json`, listing every file with its SHA-256.

Every GLB uses the same canonical 71-joint rig in XNA's exact topology: meters, Y up, facing +Z,
feet on y = 0, the avatar's left on +X. Joints XNA leaves unnamed are helpers named `SlotNN`,
never skinned or animated. Materials are a base color factor, an optional embedded base-color PNG
(a near-white multiplier carrying shading and fabric detail) and a description color tint. The
reader refuses anything outside that contract: external URIs, other rigs, non-identity bind
rotations, out-of-range indices or weights, and oversized data. Catalog v2 keeps to what the
format 1 reader accepts (its normals and texture coordinates are normalized 16-bit accessors),
so older CNA builds can draw v2 items fetched from a service; they ignore facial hair, face
controls and hat variants. `GamerServices_AvatarCatalogUpToDate` regenerates the newest catalog
and compares it byte for byte; `AvatarCatalogTest.CatalogV1IsFrozen` and
`V1DescriptionsAssembleExactlyAsReleased` pin v1. `tools/avatar_builder/avatar_review.py` renders
review sheets through the real renderer (`cna_avatar_review`) and a CPU preview.

### Newer catalogs from the service

A description names the catalog version its items come from. For a version that is not compiled
in, the renderer's loader asks the service for that catalog's manifest (`avatars.catalog`)
and resolves each file by content hash: a file the library already has (same SHA-256) is used from
it; any other is downloaded from the service's immutable asset
store (`assets.read`), verified against the manifest hash and size, and cached on disk by hash
(`CNA_GAMER_SERVICES_CACHE_DIR`, else `$XDG_CACHE_HOME/cna/gamer-services/assets`), where every
later read is verified again. Only item files travel; bones and geometry are never streamed
during play.

An item that cannot be resolved (no service, an unknown id, a missing or corrupt file) is replaced
by the first item of its slot (optional accessories are omitted), so the avatar still renders; a
body that cannot be resolved makes the renderer `Unavailable`.
