Snapshot and confidence definitions: [main audit](gamer-services-audit.md). `GS` = `modules/gamer-services`, `NET` = `modules/net`, `S` = sibling `cna-gamer-services-server`. Source suffixes below resolve under those modules. `U` = relevant cases in the executed 627-case GamerServices suite; `N` = executed 523-case Net suite; `S-test` = fresh-server tests. These are **not** per-method exhaustive coverage certifications. Fake and real service evidence are distinguished.

**Status:** COMPLETE = fully established for stated bounded scope; MOSTLY COMPLETE = working implementation with limited unverified/missing semantics; PARTIAL = important missing behavior; STUB = callable surface without promised effect; MISSING = absent capability; BROKEN = reproduced defect; UNKNOWN = insufficient evidence. No broad area merits COMPLETE merely from this audit's finite test run.

C++ APIs use get/set property methods, references/vectors/std::any and caller-owned IAsyncResult pointers. This is source adaptation, not ABI or CLR binary compatibility. Exact historical Xbox exceptions/timing are UNKNOWN where not specifically established. See the [member-name screen](evidence/reference-member-screen.md), which does **not** verify every overload's type or semantics.

## How to use this as a roadmap

Fix reproduced BROKEN paths first, then resolve PARTIAL items needed by a concrete target game. MOSTLY COMPLETE means useful implementation evidence, not “finished forever.” UNKNOWN rows need focused validation before implementation work. The [issues](gamer-services-issues.md) give severity/effort; [handoff](gamer-services-handoff.md) gives exact commands and unverified areas.
