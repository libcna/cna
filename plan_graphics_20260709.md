| #   | Task                                                                     | Status | Notes                 |

| 664 | Fix Vulkan: multiple `SpriteBatch::Begin()`/`End()` calls per frame — only the last batch renders | ✅ | **Real, confirmed bug, root cause isolated and fixed** — instrumented/traced the Vulkan command recording first, per this row's own prior instruction, rather than guess-fixing. **Root cause (2 compounding mechanisms)**: (1) `VulkanSpriteBatchBackend::Begin()` unconditionally cleared its own `vertices_`/`indices_`/`draws_` member vectors — the *same* mutable storage a prior `End()` had just finished populating. `activeBatches_` (owned by `VulkanGraphicsBackend`) tracked entries by **raw pointer** to that single object, pushed at `Begin()` time. Since the once-per-frame harvest (`RecordCommandBuffer`, driven by `Present()`) runs strictly after all of a frame's `Begin/Draw/End` calls, a 2nd `Begin()` call destroyed the 1st cycle's already-completed geometry *before* the harvest ever got a chance to read it — by the time any Vulkan command was even recorded, the 1st batch's data no longer existed in process memory. (2) A second, latent, previously-masked bug in `drawSpritesFor`'s harvest loop: every `activeBatches_` entry was `memcpy`'d to a **hardcoded offset 0** in the shared per-frame `spriteVB_`/`spriteIB_` buffers (unlike the already-correct 3D immediate-draw path, `draw3DFor`, which uses a genuine accumulating `vbOff`/`ibOff` cursor) — so even after fixing (1), 2 *genuinely distinct* batches targeting the same render target in one frame would still stomp on each other's GPU-visible memory before `vkQueueSubmit` ran. **Fix**: added `VulkanSpriteBatchBackend::BatchSnapshot` (owns `vertices`/`indices`/`draws`/`customEffectBackend` by value); `End()` now moves the completed cycle's geometry into a freshly heap-allocated snapshot and pushes it onto `activeBatches_` (changed to `std::vector<std::pair<std::unique_ptr<BatchSnapshot>, VulkanRTSource*>>`) — not `Begin()` — so a 2nd `Begin()` call only ever resets its own not-yet-used working vectors, never a completed cycle's already-snapshotted data. Gave `drawSpritesFor` a genuine accumulating `vbOff`/`ibOff` cursor mirroring `draw3DFor`'s exact pattern (bounds-checked against `MaxSpriteVertices`/`MaxSpriteIndices`, `memcpy`'d and bound at the running offset, advanced by each snapshot's byte size after its draw calls are recorded) so multiple snapshots targeting the same RT now compose additively instead of overwriting each other. Removed the now-unnecessary `ConsumeDraws()`/`GetVertices()`/`GetIndices()`/`GetDrawCalls()`/`GetCustomEffectBackend()` accessors (snapshots are read directly by the harvest loop; destroyed en masse via the existing once-per-frame `activeBatches_.clear()`). Added `activeRT_` member to `VulkanSpriteBatchBackend`, captured at `Begin()` (preserving the original "RT active during this cycle" semantics) and used when pushing the snapshot at `End()`. **New regression test** `examples/vulkan_spritebatch_multi_begin_end_test.cpp`: 2 independent `Begin()`/`Draw()`/`End()` cycles in one `Draw(GameTime)` (Red quad left half, Blue quad right half, exactly matching the confirmed repro) — **both regions PASS with the exact predicted colors on the first attempt after the fix**. **Discriminating power independently verified**: `git stash`-reverted both changed files (header+cpp) and rebuilt — the pre-fix code reproduced the exact reported symptom (`left region = black/clear (0,0,0)` instead of Red, right region correctly Blue) confirming the test genuinely discriminates the bug; `git stash pop`-restored and reconfirmed both regions pass.
