# plan_csl.md — CSL, CSIR and the CNA Shader Rosetta Stone (`CNA::Shader`, `CNA_CSL`)

> **Base document:** [`misc/csl.md`](../misc/csl.md). That file is the *design proposal*; this file
> is its *executable task backlog*. Every task below traces back to a `misc/csl.md` section
> (`→ §12`). Where this plan contradicts `misc/csl.md`, the contradiction is listed in §0.2 and
> **this file wins** (`misc/csl.md` is amended in `CSL-46`).
>
> **Scope:** a CNA-owned shader language (**CSL**), a two-level intermediate representation
> (**CSIR-H** / **CSIR-L**), a single written-down **CNA Shader ABI**, five target backends
> (GLSL, SPIR-V, HLSL, MSL, WGSL), a compiled package format (**CSP**), a CPU reference
> interpreter, and a conformance framework that proves every CNA renderer implements the *same*
> semantics. All of it in `namespace CNA::Shader`, in `modules/shader/`, plus the runtime
> `CNAEXT CslEffect` in the XNA graphics namespace and four command-line tools.
>
> **Out of scope** (explicitly): a general-purpose GPU compute language, a C++ frontend, ray
> tracing / mesh shaders / bindless (the `Advanced` tier is *named* here and implemented nowhere),
> replacing SPIR-V with a CNA binary format, and any change to the XNA 4.0 public contract that is
> not an always-compiled `CNAEXT` marker member.
>
> **Status legend:** ✅ implemented *and verified against its stated acceptance criterion*;
> 🟨 code exists but the criterion is not met/verified; ⬜ not started; ⛔ deliberately not done
> (with the reason in the row itself, never in a commit message only).
>
> **1,173 numbered tasks across 43 phases, every one ⬜ today. Nothing in this plan has been
> implemented.** This document is the thing being approved; implementation starts after approval,
> not before. Task IDs are sparse inside each phase on purpose, so work discovered during
> implementation takes a free neighbouring number instead of forcing a renumbering pass. The
> conformance *corpus* is a separate count and is expected to pass 10,000 cases (Phases 31–35);
> a corpus case is not a task row, and `CSL-2537` is why the two are never conflated.
>
> **Created:** 2026-09-04. **Branch:** `csl`. **Build directory:** `cmake-build-csl/`.
> **Running ledger:** `NEXT_csl.md` (created in `CSL-40`) — the "what to pick up next" file, in the
> style of `NEXT_modern.md` and `NEXT_skia.md`. Task status lives *here*; the ledger holds the
> position on the critical path, the decisions that did not survive contact, and the recorded test
> baselines.

### 0.2 Corrections this plan makes to `misc/csl.md`

| # | `misc/csl.md` says | Reality / decision |
|---|---|---|
| C1 | §34: a top-level `spec/` directory with six `.md` files | There is no `spec/` in this repository and specifications live in `docs/`. **Decision:** `docs/csl/{csl-language,csir,shader-abi,shader-profiles,shader-package,conformance,architecture}.md`. `docs/csl/architecture.md` is the home of the §49 rule. |
| C2 | §34: `modules/shader/{frontend,ir,backends,reflection,optimizer,validator,package}/` as module-root directories | CLAUDE.md fixes the module shape: `modules/<name>/{CMakeLists.txt,include/,src/,tests/,examples/}` with `include/` reproducing the namespace path. **Decision:** `modules/shader/include/CNA/Shader/<Area>/…` and `modules/shader/src/<Area>/…` with the same `<Area>` names (`Csl`, `Ir`, `Backends`, `Reflection`, `Optimizer`, `Validator`, `Package`, `Interpreter`, `Fx`, `Effect`). See `CSL-3` and `CSL-47`. |
| C3 | §1: the tool names `cna-shaderc`, `cna-shader-info`, `cna-shader-test`, `cna-shader-diff` | Kept verbatim as the *installed* names. Their sources live under `tools/csl/`, matching `tools/<area>/` (`tools/content/`, `tools/cnb/`). |
| C4 | "46 renderers" throughout | 49 public renderer identities across 36 family directories. Phase 25 covers **all 49**, and a renderer identity that has no shader pipeline at all is a first-class outcome, not a gap (§33). |
| C5 | §12: a renderer declares `ShaderTargetProfile Renderer::shaderTarget()` | A dialect hook **already exists** (`ShaderDialectEXT`/`GetShaderDialectEXT`) and one renderer already answers it. **Do not add a second, competing mechanism.** A target *profile* is finer than a dialect (`glsl-330` vs `GlslDesktop`), so the new virtual returns a profile and the existing dialect becomes a derived, non-authoritative projection of it (`CSL-912`, `CSL-913`). |
| C6 | §10: capabilities are a new, CSL-private list | `CNA::RendererFeature` is append-only, public, already exposed through the C ABI, and already carries six shader-dialect entries. **Decision:** CSL capability requirements map onto `RendererFeature` wherever one exists, and only genuinely new shader-language capabilities get new enumerators (`CSL-628`). Two parallel capability vocabularies is the failure this correction exists to prevent. |
| C7 | §16/§21: `cna-shader-info StandardLit.cnb` and `content.Load<Shader>("StandardLit")` | CNB is a container; the shader asset inside it is a **CSP** payload. The tool reads `.csp`, and a `.cnb`/`.xnb` **containing** one, and says which it found. `ContentManager::Load<CslEffect>` is the runtime call — there is no XNA type named `Shader` and this plan does not invent one. |
| C8 | §26: "a simple CSIR interpreter on the CPU" for the Core tier | Kept, but with a consequence the proposal does not draw: an interpreter that is only *approximately* IEEE-754 is worse than none, because it becomes a second source of truth. **Decision:** the interpreter is bit-exact for `float32` arithmetic under a stated rounding contract, and every operation it *cannot* make exact (transcendentals, texture filtering) is declared `tolerance`-only in the spec and in the manifest (`CSL-1335`, `CSL-1384`). |
| C9 | §5: "no pointers of any kind" | Kept for the language, but `out`/`inout` parameters are **not** pointers and are required by the FX frontend (§14) and by XNA-style helper functions. They are in CSL v1 (`CSL-296`). |
| C10 | §22/§29: "10,000+ conformance cases" as a target | Kept as an outcome, refused as a target. A generated case that no backend can fail is corpus weight, not coverage. **Decision:** the corpus is sized by the *generators*' declared coverage matrices (Phase 35), and the dashboard reports both the case count **and** the number of cases that have ever discriminated between two backends (`CSL-2537`). |
| C11 | §17: `--targets all` | Kept, but `all` means *every profile this build of `cna-shaderc` can emit*, and the package records which profiles were requested and which were skipped, so a missing variant at runtime is a diagnosable fact rather than a silent absence (`CSL-1567`). |
| C12 | §40: the "CNA Shader Laboratory" GUI | Kept, last (Phase 40), and deliberately built on the same public API as `cna-shaderc --dump-ir` so it can never become a second compiler driver. |

### 0.3 Definition of Done (applies to **every** task in this file)

A task is ✅ only when all of these hold:

1. `// SPDX-License-Identifier: MS-PL` on every new `.hpp` and `.cpp`.
2. Full Doxygen (`@brief`/`@param`/`@return`) on **every** public member, per CLAUDE.md verbatim.
3. Builds clean **both** with `-DCNA_CSL=ON` (default) and `-DCNA_CSL=OFF`.
4. Google Test coverage for every new public method/overload/operator/constant, under the owning
   module's `tests/` mirroring the namespace path.
5. No new production `.cpp` outside a module directory (the physical source-partition validator).
6. No new third-party library is linked. External shader tools may be *invoked by tests* only
   through the oracle harness of `CSL-2001`, which **skips** rather than fails when absent.
7. One task = one commit, `feat(CSL-nnn): …` / `fix(CSL-nnn): …` / `test(CSL-nnn): …`, staged by
   explicit filename.
8. The task's row in this file is flipped to ✅ **in the same commit**, carrying the acceptance
   evidence — the measured number, the test name, the file and line — not a restatement of the task.
9. A row that turns out to be wrong is answered in the row (⛔ with the reason), never deleted.

## 1. Architecture decisions locked in by this plan

| ID | Decision |
|---|---|
| D1 | **CSL + CSIR is the reference.** GLSL, HLSL, SPIR-V, MSL and WGSL are *implementations* of a meaning defined here, never definitions of it. Written in capitals in `docs/csl/architecture.md` (`CSL-60`). Any disagreement between a backend and the spec is a backend bug until the spec is amended by a numbered row. |
| D2 | **CNA owns every emitter.** No shader toolchain is vendored or linked. `CSIR-L → SPIR-V` emits binary words directly; `CSIR-L → GLSL/HLSL/MSL/WGSL` emits source text directly. External tools (`spirv-val`, `glslang`, `naga`, `tint`, DXC, `fxc`, `libshaderc`) are **oracles used by tests only**, discovered at run time, and their absence SKIPs a test rather than failing it. |
| D3 | **A renderer never contains a compiler.** A renderer declares a `ShaderTargetProfile` and consumes the artifact it is handed. Any renderer-specific transformation is a *legalization pass inside the backend* (Phase 13), named after the profile, not the renderer. |
| D4 | **Purely additive.** `ShaderEffect`, the compiled `.fx`/MojoShader path (`plan_fx.md`), the content pipeline's external-`fxc` route, and every `CNA::Graphics` pass keep working byte-identically and are not modified. Unification is re-decided on evidence in Phase 41, not assumed here. |
| D5 | **`CNA_CSL=ON` by default; `CNA_CSL_CONFORMANCE=OFF` by default.** The compiler is host-side C++23 with no new dependencies and the tools need it. The corpus is thousands of cases and wants a real GPU, so it is opt-in. `CNA_CSL=OFF` must produce a tree byte-identical in behaviour to today. |
| D6 | **The capability vocabulary is `CNA::RendererFeature`.** CSL requirements map onto it; new enumerators are appended only when no existing one expresses the requirement, and each addition is its own row. |
| D7 | **Refusal is a feature.** A shader whose requirements a renderer cannot meet is refused **before** compilation, by name, with the missing capability named. There is no "approximate it somehow" path anywhere in this plan (§10). |
| D8 | **Determinism over speed, everywhere.** The compiler is deterministic: same input, same compiler version → byte-identical output, verified by a row (`CSL-1916`). The interpreter is exact where it claims to be and tolerance-only where it is not. |
| D9 | **The offscreen framebuffer is the conformance surface.** Never the swapchain, never a screenshot (§24). A render test that cannot read back its result does not run on that renderer, and says so. |
| D10 | **Every artifact carries its provenance.** Source hash, compiler version, CSIR version, profile, and the requirement set travel inside the CSP. A variant that cannot be traced to a source cannot be loaded. |
| D11 | **The whole subsystem is renderer-agnostic by construction.** `modules/shader` links `cna_core` and `cna_math` and nothing else — no renderer target, no `cna_graphics`. The dependency runs `graphics → shader`, never back. |
| D12 | **Non-executable targets are honest.** HLSL/MSL cannot be built or run on the Linux machine this work happens on (the same constraint `plan_fx.md` records). Their rows are ✅ only for what *is* verifiable here — emission, golden text, self-consistency, and any oracle that exists — and 🟨 with the reason for anything needing the real API. Never ✅ by assertion. |
| D13 | **The interpreter is not a renderer.** It answers "what should this shader produce", it never enters a frame. It lives behind `CNA_CSL` in `modules/shader`, not in `modules/renderers/software`. |

## Phase 0 — Foundation: module, build wiring, conventions, ledger (`CSL-1`–`CSL-48`)

Nothing compiles a shader in this phase. It makes the subsystem buildable, testable, documented and
discoverable, so every later phase has one place to add a header, a test and a doc line.

## Phase 11 — Optimizer (`CSL-795`–`CSL-815`)

Deliberately modest. The optimizer exists to make generated source readable and to remove what
lowering introduced — not to compete with the driver's compiler, which will run afterwards anyway.

| ID | Task | Status | Acceptance criterion |
|---|---|---|---|
| CSL-795 | Pass manager with named passes, an ordered pipeline and per-pass statistics | ⬜ | `--print-pass-stats` reports instructions before/after per pass; the pipeline for each `-O` level is data, listed in `docs/csl/architecture.md`. |
| CSL-796 | `-O0`, `-O1`, `-O2` levels with documented pass lists | ⬜ | `-O0` runs only the passes correctness requires (there are some — see `CSL-801`); the levels are stable and a test pins each list. |
| CSL-797 | **Every pass preserves semantics, and that is tested, not asserted** | ⬜ | For every pass, a differential test runs the corpus through the interpreter (Phase 19) with the pass on and off and asserts bit-identical results for exact-class operations. | CSL-798 | Constant folding | ⬜ | Uses the same evaluator as `CSL-387`, so a folded expression and a runtime one cannot differ (`CSL-388`). |
| CSL-799 | Constant propagation | ⬜ | Tested; interacts correctly with specialization constants, which must *not* be folded before specialization. |
| CSL-800 | Dead-code elimination | ⬜ | Removes unused instructions and unreachable blocks; never removes a `discard`, a barrier, an atomic or a storage write, which is the test. |
| CSL-801 | Mandatory cleanup pass, run even at `-O0` | ⬜ | Removes the redundancy lowering itself creates (identity conversions, trivial copies) so `-O0` output is readable; documented as correctness-neutral but required for legibility. |
| CSL-802 | Common subexpression elimination within a block | ⬜ | Conservative across memory operations and texture fetches; a test asserts two identical texture samples with a store between them are *not* merged. |
| CSL-803 | Copy propagation | ⬜ | Tested, including through `out` parameters. |
| CSL-804 | Algebraic simplification, restricted to identities that are bit-exact in IEEE-754 | ⬜ | `x*1`, `x+0`, `x-0`, `x/1` are folded; `x*0 → 0` is **refused** (NaN, −0) and the refusal is a documented row outcome, not an omission. |
| CSL-805 | Vector-construct/extract simplification | ⬜ | `float4(v.x,v.y,v.z,v.w) → v` and swizzle-of-swizzle collapsing; measured on the corpus for how many instructions it removes. |
| CSL-806 | Function inlining, with a size heuristic and a hard depth limit | ⬜ | Required for profiles that cannot express user functions at all; the heuristic is documented and the limit is tested at the boundary. |
| CSL-807 | Full inlining mode for profiles with no function support | ⬜ | `--inline-all`; a test asserts the resulting module has exactly one function per entry point. |
| CSL-808 | Loop unrolling for statically countable loops, gated by a size budget | ⬜ | Required by ES 1.00-class profiles; the budget is a number in the profile table, and exceeding it is `CSL4010` rather than a 30-second compile. |
| CSL-809 | Branch simplification for constant conditions | ⬜ | Removes the dead arm and its blocks; interacts correctly with specialization constants (the same care as `CSL-799`). |
| CSL-810 | Uniform-block member elimination is **refused** | ⬜ | ⛔ by design: removing an unused member changes offsets and breaks every caller's uploads. The row records the refusal so a future contributor does not "optimize" it in. |
| CSL-811 | Instruction scheduling / reassociation is **refused** | ⬜ | ⛔: floating-point reassociation is not value-preserving and the driver will schedule anyway. Recorded with the reason. |
| CSL-812 | Pass ordering is fixed and its effect is measured | ⬜ | Instruction counts for the corpus at each level, recorded in `NEXT_csl.md`, so a future pass can be judged on evidence. |
| CSL-813 | Optimizer fuzz: random modules through the whole pipeline never crash and never change results | ⬜ | Combined with the Phase 19 interpreter; 1e6 executions; every divergence becomes a committed regression module. |
| CSL-814 | Debug-info preservation policy | ⬜ | Passes preserve source locations or explicitly drop them via one helper that records which pass dropped what; `--dump-ir` shows the provenance. |
| CSL-815 | `--no-opt` produces IR whose printed form maps one-to-one onto the source | ⬜ | Used by the Shader Laboratory (Phase 40) and by anyone debugging the compiler; tested by counting instructions against a hand-computed expectation for `CSL-99`. |

## Phase 19 — CPU reference interpreter (`CSL-1335`–`CSL-1388`) — **Milestone 6**

→ §26, §27, and correction C8. This is the phase that makes D1 more than a slogan: after it, no
GPU is the truth. It needs no renderer and can be built the moment Phase 12 lands, which makes it
the best parallel track in the plan.

### 19.1 Numeric contract

| ID | Task | Status | Acceptance criterion |
|---|---|---|---|
| CSL-1335 | The exactness contract, written down before any code | ⬜ | `docs/csl/conformance.md` §Exactness: which operations are **exact** (bit-identical to correctly-rounded IEEE-754 binary32 round-to-nearest-even) and which are **tolerance** with a per-operation ULP budget. | CSL-1336 | Host float determinism: no x87, no FMA contraction, no fast-math | ⬜ | Compiled with the flags that guarantee it (`-ffp-contract=off`, no `-ffast-math`), asserted by a test computing a value that differs under contraction. | CSL-1339 | Integer semantics: wrapping, shifts, division by zero | ⬜ | Exactly as the spec says, including the shift-amount rule of `CSL-445` and the defined-or-UB status of integer division by zero. |

### 19.2 Execution engine

| ID | Task | Status | Acceptance criterion |
|---|---|---|---|
| CSL-1345 | `Interpreter` executing CSIR-L (→ `CSL-867`) | ⬜ | Takes a module, an entry point, a resource-binding set and an invocation index; returns the outputs. No renderer, no GPU, no threads. |

| CSL-2824 | CI job: sanitizer build of the shader tests | ⬜ | ASan+UBSan; the row records the runtime cost. |
| CSL-2825 | CI job: the determinism check (`CSL-1916`) | ⬜ | Two builds, byte-compared. |
| CSL-2826 | CI job: golden freshness, matrix freshness, doc/table sync | ⬜ | `CSL_GoldenFresh`, `CSL_MatrixFresh`, `CSL_GrammarSync`, `CSL_BuiltinSync`, `CSL_CapabilitySync`, `CSL_CsirNodeSync`, `CSL_DiagnosticCoverage`, `CSL_ValidatorRuleCoverage`, `CSL_AreaLayering`, `CSL_RendererBoundary`, `CSL_DeterminismLint` — eleven gates, all registered, all green. |
| CSL-2827 | Compile-time budget for the subsystem | ⬜ | `cna_shader`'s full build time measured and recorded; a ceiling with a documented margin, since a compiler is exactly the kind of code that quietly triples a build. |

## 3. Risks, and what this plan does about each

| # | Risk | Mitigation, by row |
|---|---|---|
| R1 | **The compiler becomes a second source of truth against the spec.** | Every table is checked against its document by a ctest (`CSL_GrammarSync`, `CSL_BuiltinSync`, `CSL_CapabilitySync`, `CSL_CsirNodeSync`); the spec's example shaders are corpus cases asserted byte-identical (`CSL-99`). |
| R2 | **The corpus grows huge and proves nothing** (C10). | Generated cases compute expectations independently of CSL (`CSL-2423`); the dashboard reports discrimination, not volume (`CSL-2537`); dead families are reported (`CSL-2435`). |
| R3 | **The interpreter is subtly wrong and becomes an authoritative lie.** | The exactness contract is written before the code (`CSL-1335`); it is differentially tested against three real GPUs (`CSL-1381`–`CSL-1383`); it is never the oracle for a tolerance-class result (`CSL-1384`). |
| R4 | **A backend re-decides a semantic the spec fixed.** | Semantics are resolved into distinct CSIR opcodes before any backend sees them (`CSL-543`, `CSL-852`); cross-backend structural assertions compare the generated artifacts programmatically (`CSL-2215`). |
| R5 | **Renderers grow shader-compiler code.** | D3, plus a mechanical gate (`CSL-48`, `CSL-1816`). |
| R6 | **HLSL and MSL are "done" without ever running.** | D12; those rows are 🟨 with the blocker named, never ✅ by assertion (`CSL-1176`, `CSL-1242`). |
| R7 | **The subsystem destabilizes the existing tree.** | D4/D5; `CNA_CSL=OFF` parity is a standing CI gate (`CSL-8`, `CSL-2823`); the final full-suite comparison against a recorded baseline is a row (`CSL-41`, `CSL-2747`). |
| R8 | **Scope creep into a general GPU language.** | The §48 refusals are in the spec (`CSL-65`), the Advanced tier is named and unimplemented (`CSL-625`), and `sm2`, geometry/tessellation stages and a full HLSL parser each have an explicit ⛔ row. |
| R9 | **Determinism is assumed rather than achieved.** | A lint (`CSL-21`), canonical ordering at three levels (`CSL-562`, `CSL-863`, `CSL-1561`), and one end-to-end verification row (`CSL-1916`). |
| R10 | **The plan outlives its own accuracy.** | Status is regenerated by a script (`CSL-2749`), every ⛔ carries its reason in the row, and the evidence audit (`CSL-2847`) is itself a row. |

## 4. Owner decisions (answered 2026-09-04)

All six questions this plan raised are answered. They are recorded here **and** in the row that
owns each one, so a future reader meets the decision where the work is, not only in a table. A row
implementing one of these may not quietly re-decide it; reopening one is its own new row.

| # | Question | Owner's answer | Effect on the plan |
|---|---|---|---|
| Q1 | Should `SOFTWARE` gain a real shader pipeline by running CSIR-L through the interpreter? | **No for v1; re-decide on measured throughput.** | `CSL-1804` answers "none" and behaves like `HEADLESS` — a conformance run against it SKIPs and never reports a pass. `CSL-2744` re-decides it in Phase 41 on the `CSL-1385` measurement. |
| Q2 | Is a `CSIR → bgfx` profile wanted? | **Out of v1 scope; a named future profile.** | `CSL-1787` answers "none" with the reason and records `CSIR → bgfx binary` as a legitimate future profile rather than a gap. The existing `bgfx_shaders.hpp` route is untouched. |
| Q3 | Does the FX frontend replace MojoShader, or complement it? | **Complementary; both keep working.** | D4 stands. `CSL-1486` states the two routes and which input each takes; `CSL-1630` defaults to the existing MojoShader route so nothing changes silently; D3D9 stays MojoShader-only (`CSL-1178`, `CSL-1795`). |
| Q4 | Does the Shader Laboratory ship? | **Developer tool, off by default.** | Phase 40 keeps its own CMake option (`CSL-2704`); a default build is unaffected; it is built strictly on the public API (C12). |
| Q5 | Separate `.csle` file, or an `effect { }` block inside `.csl`? | **Separate `.csle` file** — against this plan's own lean. | The largest change of the six. `CSL-1431` now *refuses* the in-`.csl` block by name, and seven rows carry the cost the separate file creates: `CSL-1441` (path references), `CSL-1442` (the dependency edge as one queryable API), `CSL-1443` (diagnostics across the edge), `CSL-1636`/`CSL-1637` (second content-pipeline input type and its incremental-build edge), `CSL-1858` (hot reload follows the edge) and `CSL-1922` (`cna-shaderc --deps`). |
| Q6 | How much GPU CI is available? | **None. Assume the worst.** | `CSL-2822` adds no CI job and instead writes the consequence down: the interpreter-only run (`CSL-2821`) is the standing gate, GPU runs are manual, and a certification record is a human point-in-time measurement rather than a continuously-enforced property. |

**What Q6 costs, stated plainly.** With no Windows and no macOS runner, `CSL-1176`, `CSL-1177` and
`CSL-1242` cannot reach ✅ inside this plan — **M3 and the Metal half of M5 stay 🟨 by construction,
not by neglect.** D12 already required that; Q6 makes it permanent rather than provisional. Those
branches are verified here by golden text, structural assertions against the IR (`CSL-1175`), the
partial MSL checker (`CSL-1243`) and any oracle that happens to be installed — and by nothing else.
The plan does not pretend otherwise, and no row may flip them to ✅ without a machine that ran them.
