# OPENGL1 backend tests

Configure CNA with `-DCNA_GRAPHICS_BACKEND=OPENGL1` on Linux or Windows. The backend requires a desktop OpenGL compatibility implementation. Linux CI can use Xvfb plus Mesa/llvmpipe; Windows CI can at minimum compile/link the backend and run on a software/VM OpenGL implementation where available.

Run the suite with `ctest -R "OpenGL1_"` from the build directory (needs `-DCNA_BUILD_TESTS=ON -DCNA_BUILD_EXAMPLES=ON`, real `DISPLAY`/Xvfb; see `cmake/Tests/OpenGL1Tests.cmake`).

The shared, backend-agnostic `CnaTests` gtest binary also builds and mostly passes under `CNA_GRAPHICS_BACKEND=OPENGL1` (plan_opengl1.md phase 12's Reach-profile audit ran it in full for the first time). Two shared test files had EasyGL-only/D3D9-only-shaped assumptions that didn't anticipate OPENGL1 as a second, legitimately-different 3D-capable backend -- both fixed with `#ifdef CNA_BACKEND_OPENGL1` branches, see plan_opengl1.md phase 12 for the detail. The other ~126 `CnaTests` failures on this sandbox are pre-existing and environment-specific (Media/Video/Sound/Xnb content fixtures needing files/codecs this sandbox doesn't have), unrelated to OPENGL1.

Priority runtime smoke coverage, each wired to a real CTest registration:
1. clear + present — `OpenGL1_PixelTestGame_Smoke`;
2. SpriteBatch textured quad — `OpenGL1_TexturedQuad_Readback`;
3. colored 3D triangle with depth — `OpenGL1_RasterizerState_CullMode`;
4. textured 3D triangle — `OpenGL1_BasicEffect_TextureEnabled`;
5. indexed cube with depth/culling — `OpenGL1_RasterizerState_CullMode_IndexedBasicEffect`;
6. fixed-function directional lighting on `VertexPositionNormalTexture` — also `OpenGL1_RasterizerState_CullMode_IndexedBasicEffect` (uses `BasicEffect.EnableDefaultLighting()`);
7. fog and alpha-test approximations — `OpenGL1_Fog_AlphaTest` (`examples/opengl1_fog_alphatest_test.cpp`, OPENGL1-specific: asserts only the qualitative/coarse behavior this backend's real fixed-function `GL_FOG`/`glAlphaFunc` approximation can honestly claim — see that file's header for why the shader-exact EasyGL fog/alpha-test files aren't reused as-is);
8. stencil and scissor state — `OpenGL1_Scissor` + `OpenGL1_DepthStencilState_StencilOps`.

Scenarios 1-6 and 8 reuse already-verified, backend-agnostic example sources (real public `Game`/`GraphicsDevice`/`BasicEffect`/`SpriteBatch` API only) from `examples/`, confirmed by inspection to contain no EasyGL-specific code before reuse.

Additional coverage beyond the 8 priority scenarios:
- `OpenGL1_Anisotropic_GlState` (`examples/opengl1_anisotropic_gl_state_test.cpp`) — plan_opengl1.md phase 1's real consumer: verifies `GL_EXT_texture_filter_anisotropic` detection (`OpenGL1Capabilities`) actually reaches the driver through `SamplerState`/`ApplySamplerState()` — sub-cap request round-trips, an over-cap request gets clamped to the driver's real max, and switching back to a non-anisotropic filter resets `GL_TEXTURE_MAX_ANISOTROPY_EXT` to 1.0 rather than leaking stale state. Skips cleanly (exit 0) if the extension genuinely isn't present.
- `OpenGL1_RenderTarget2D_Sample` — plan_opengl1.md phase 2 (RenderTarget2D via FBO): reused verbatim from the SDL_Renderer backend's own Task 705 test (`examples/sdlrenderer_rendertarget2d_sample_test.cpp`, backend-agnostic). Draws a distinctive corner marker into a render target, unbinds it, then samples it back as a plain `Texture2D` via `SpriteBatch` — the marker's position surviving the round trip is exactly the proof that render-target orientation (see "Bugs found" below) is handled correctly.
- `OpenGL1_DualTextureEffect_Doubling` — plan_opengl1.md phase 3 (`ARB_multitexture`/core-1.3 dual-texture path): reused verbatim from EasyGL's own Task 383 test (`examples/easygl_dualtextureeffect_doubling_test.cpp`, backend-agnostic). Isolates FNA's real `texture0.rgb *= 2` doubling factor (`tex0=gray(100), tex1=white → gray(200)`, distinct from the `gray(100)` a naive multiply-without-doubling would produce) from a plain sanity check (`two white textures, diffuse=red → red`).
- `OpenGL1_GraphicsCapability` (`examples/opengl1_graphics_capability_test.cpp`) — plan_opengl1.md phase 11: locks in `GraphicsDevice::SupportsCapability()`'s truth table against concrete evidence rather than just the flag value — `AnisotropicFiltering` is cross-checked against `glGetString(GL_EXTENSIONS)` directly, `OcclusionQuery=false` is cross-checked against a real `OcclusionQuery` object that never completes, and `WireFrame=true` is cross-checked against an actual `glGetIntegerv(GL_POLYGON_MODE)` readback after setting `FillMode::WireFrame`.
- `OpenGL1_BasicEffect_Combined` — plan_opengl1.md phase 4 (fixed-function texture environment/combine mappings): reused verbatim from EasyGL's own Task 370 capstone test (`examples/easygl_basiceffect_combined_test.cpp`, backend-agnostic). Asserts the exact multiplicative formula `TextureColor x VertexColor x (DiffuseColor+EmissiveColor)` across 4 independently-colored texels — this is the test that caught `DrawInternal`'s stride==16/24 paths ignoring `diffuseColor` entirely (see "Bugs found" below).
- `OpenGL1_EnvironmentMapEffect` (`examples/opengl1_environmentmapeffect_test.cpp`, OPENGL1-specific) — plan_opengl1.md phase 5 (`ARB_texture_cube_map` cube maps + `EnvironmentMapEffect`'s fixed-function reflection-mapping subset). Uses a solid-color cube map to isolate the `GL_REFLECTION_MAP`/`GL_INTERPOLATE` blend formula from reflection-vector face selection: `Amount=0`/`1` prove each term is fully suppressed in turn, `Amount=0.5` proves the blend is a genuine `mix()` and not a saturating additive combine (same 0/1-blind-spot precedent `docs/environmentmapeffect-support.md`'s own Task 383/394 already established). Pixel-exact on the first attempt. Deliberately does not test Fresnel edge-weighting or `EnvironmentMapSpecular` — both are documented, intentional OPENGL1 fixed-function limitations (see the test file's own header and plan_opengl1.md).
- `OpenGL1_ContextLoss` (`examples/opengl1_context_loss_test.cpp`, OPENGL1-specific) — plan_opengl1.md phase 8 (context-loss resource recreation registry). Draws a `Texture2D`, calls `dev.GetBackend().DebugSimulateContextLoss()` (destroys and recreates the real SDL GL context), then re-draws and reads back the SAME pixel to prove `OpenGL1ResourceRegistry` actually rebuilt the texture from its retained CPU-side pixel data rather than leaving a stale/blank handle. Does the same directly (`TextureCube::GetData()`, no draw needed) for a `TextureCube` face, plus confirms a never-written face survives recovery without crashing — this closed plan_opengl1.md phase 8's own previously-documented gap (`ITextureCubeBackend` gained a `ShareCpuPixels(face,...)` hook, added with a default no-op so every other backend stays source-compatible). Separately keeps a `RenderTarget2D` bound as the ACTIVE render target *through* the simulated loss and reads its own FBO back directly via `RenderTarget2D::GetData()` (not indirectly through `SpriteBatch`/the backbuffer — see plan_opengl1.md phase 8's own writeup for why that indirect approach can't actually discriminate a real bug) to prove `OpenGL1GraphicsBackend` correctly re-binds it after recovery, not silently leaving every post-recovery draw landing on the backbuffer instead. This test has caught 2 real, mutation-tested bugs across two nights of work — see plan_opengl1.md phase 8 for the full writeup.
- `OpenGL1_GoldenImage_Smoke`, `OpenGL1_BasicEffect_Golden`, `OpenGL1_SpriteBatch_Rotation_Golden`, `OpenGL1_TextureFilter_Linear_Golden`, `OpenGL1_BlendState_Additive_Golden`, `OpenGL1_DualTextureEffect_Golden`, `OpenGL1_RasterizerState_CullMode_Golden`, `OpenGL1_DepthStencilState_WriteEnable_Golden`, `OpenGL1_AlphaTestEffect_Golden` — plan_opengl1.md phase 10 (visual golden-image tests): 9 of EasyGL's own golden-image `.cpp` files reused verbatim (backend-agnostic, real public API only), each comparing an 8x8 live-rendered region against the EXACT same checked-in `examples/golden/*.png` EasyGL uses, via the shared `PixelTestGame::CompareGoldenImage()` helper — no new reference images. All 9 pixel-match on the first attempt despite OPENGL1's completely different (legacy fixed-function/immediate-mode) rasterizer, because every reused scene was originally chosen for a flat, edge-free sample region (constant UV, no antialiased boundary inside the checked 8x8 box). `PbrEffect`/`SkinnedEffect`/`SkinnedPbrEffect`/`EnvironmentMapEffect`'s own golden scenes are deliberately NOT reused — see plan_opengl1.md phase 10 for why.
- `OpenGL1_MipmapGeneration` (`examples/opengl1_mipmap_generation_test.cpp`, OPENGL1-specific) — plan_opengl1.md phase 6 (automatic mipmap generation). A single-pixel checkerboard texture's 2x2 box average is EXACTLY uniform gray at every mip level beyond level 0 regardless of driver-specific averaging/LOD-rounding details, making it a robust discriminator: sampled at native size it reads sharply aliased (near-white), minified 4x with `TextureFilter.LinearMipPoint` it reads exact `(128,128,128)` mid-gray — proof the mip chain was both generated (via `glGenerateMipmap`/`GL_GENERATE_MIPMAP`/CPU box-filter, whichever the driver supports) and actually sampled (via `ApplySamplerState`'s now-full 9-value `TextureFilter`→GL min/mag mapping, not just the old flat Point-vs-Linear split).
- `OpenGL1_SamplerState_BindOrder` (`examples/opengl1_samplerstate_bind_order_test.cpp`, OPENGL1-specific) — 3 real SamplerState bugs found and fixed the same day as phase 6 (see plan_opengl1.md phase 6's own "Adjacent finding" entry for the full writeup): `ApplySamplerState` firing before the corresponding texture is bound, its `slot` parameter being ignored entirely, and `SpriteBatch`'s own address-mode never being applied. Mutation-tested: temporarily reverted the fix, confirmed both checks fail with the exact predicted wrong values, restored the fix, reconfirmed the exact predicted correct values. Deliberately uses the non-default `TextureAddressMode.Clamp` and grayscale-magnitude texels rather than the more obvious red/green + default-Wrap design — an earlier version of this test using the XNA default (`Wrap`) passed even against the deliberately-reintroduced bug, because the bug's fallback behavior coincidentally also produces `Wrap`-like results; this is exactly the kind of false-negative this project's own "verify against the real driver, not by inspection" culture exists to catch.
- `OpenGL1_SwapInterval` (`examples/opengl1_swapinterval_test.cpp`, OPENGL1-specific) — plan_opengl1.md item 20 (EasyGL parity: runtime `SetSwapInterval()`). Before this, `OpenGL1GraphicsBackend` never overrode `IGraphicsBackend::SetSwapInterval()` at all (inherited the interface's no-op default) — only the construction-time value ever reached SDL, so a runtime vsync change silently did nothing. Verified directly against the real driver via `SDL_GL_GetSwapInterval()`: `SetSwapInterval(0)` then `SetSwapInterval(1)`, asserting the driver reports `0` then `1` — the second call proves this is a genuine runtime change and not a value that merely happened to already match construction time. Mutation-tested: reverting the override to a no-op reproduces the predicted failure (`SDL_GL_GetSwapInterval=1` after `SetSwapInterval(0)`); restoring the fix reproduces the predicted correct values.

## Bugs found and fixed while wiring this suite up

- `OpenGL1GraphicsBackend::glContext_` was `void*` instead of `SDL_GLContext` — didn't compile against SDL3's typed `SDL_GL_MakeCurrent`/`SDL_GL_DestroyContext`.
- `ApplyRasterizerState` mapped `CullMode::CullClockwiseFace`/`CullCounterClockwiseFace` to `glCullFace(GL_FRONT/GL_BACK)` backwards relative to GL's default CCW-front convention — XNA's default `RasterizerState` (`CullCounterClockwiseFace`) was back-face-culling every `SpriteBatch` quad and any 3D triangle with the same winding, so nothing but the `Clear()` color ever reached the screen.
- `OpenGL1SpriteBatchBackend::Draw()` translated by `(dest + origin)` before rotating and then subtracted `origin` again, double-applying the origin offset instead of leaving it invariant under rotation (same bug class as the SDL_Renderer backend's own Task 671 fix).
- `DrawInternal`'s stride==20 (`VertexPositionTexture`) vertex path hardcoded `glColor4f(1,1,1,1)`, silently ignoring `GpuDrawParams::diffuseColor` — any `BasicEffect.TextureEnabled` draw with a non-white `DiffuseColor` and no vertex-color channel rendered with the tint completely missing.
- `OpenGL1GraphicsBackend` requested `SDL_GL_STENCIL_SIZE=8` only in its own constructor, which runs after `GraphicsDevice` has already created the SDL window. On X11/GLX (unlike EasyGL's ES/EGL context path, which can defer config selection to `SDL_GL_CreateContext()` time), the window's visual — and therefore its depth/stencil buffer bits — is fixed at `SDL_CreateWindow()` time; the late request was silently dropped, producing a 0-bit stencil buffer and making every `DepthStencilState.StencilEnable` a permanent no-op. Fixed by requesting `SDL_GL_STENCIL_SIZE`/`SDL_GL_DEPTH_SIZE`/`SDL_GL_DOUBLEBUFFER` in `GraphicsDevice.cpp` before `SDL_CreateWindow()` for `CNA_BACKEND_OPENGL1`, in addition to the (still-needed, now-redundant-but-harmless) request in the backend's own constructor. Confirmed empirically via `glGetIntegerv(GL_STENCIL_BITS)`: 0 before the fix, 8 after.
- `ReadBackbuffer` was unimplemented (inherited the default that throws), so `GraphicsDevice::GetBackBufferData()` — and therefore every pixel-readback test in this suite — could not run at all against this backend. Implemented via `glReadPixels` off `GL_BACK`, matching the EasyGL backend's own y-flip convention.
- `OpenGL1SpriteBatchBackend::Begin()` never disabled `GL_CULL_FACE` — real XNA `SpriteBatch` is never subject to 3D face culling, but a game's `RasterizerState.CullMode` could silently make sprites disappear depending on winding. Latent on the backbuffer (the fixed quad winding happened to survive the default state); became directly observable once render-target rendering exercised a genuinely different code path. See plan_opengl1.md's "Bugs found while adding test coverage" section for this and two more (`GL_CLAMP` vs `GL_CLAMP_TO_EDGE`, and render-target texture-sampling orientation) found while getting `OpenGL1_RenderTarget2D_Sample` green.
- `DrawInternal`'s stride==16 (`VertexPositionColor`) and stride==24 (`VertexPositionColorTexture`) vertex paths used the raw per-vertex color alone (`glColor4ub`), silently ignoring `GpuDrawParams::diffuseColor` — the same bug class as the stride==20 fix above, but for the vertex-color paths. XNA's real `BasicEffect.VertexColorEnabled` formula multiplies vertex color BY the material's `(DiffuseColor+EmissiveColor)*Alpha`, not vertex color alone. Fixed with an `emitVertexColor` lambda that does the component-wise multiply before `glColor4f`. Caught by `OpenGL1_BasicEffect_Combined`.
- `DrawInternal`'s lit (stride 32, `VertexPositionNormalTexture`) path enabled `GL_COLOR_MATERIAL`/`GL_AMBIENT_AND_DIFFUSE` but never set `GL_EMISSION` — any lit draw's `EmissiveColor` (`BasicEffect`) or combined `EmissiveColor`+`AmbientLightColor*DiffuseColor` (`EnvironmentMapEffect`) was silently dropped from the rendered color entirely. Fixed with `glMaterialfv(GL_FRONT_AND_BACK,GL_EMISSION,...)` from `GpuDrawParams::emissiveColor`. Caught while building `OpenGL1_EnvironmentMapEffect` — its `Amount=0` case would have read back black instead of the expected ambient-only base color without this fix.
