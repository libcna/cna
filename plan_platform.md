# CNA Platform Abstraction (`IPlatform`) — Implementation Plan

> **Status: PLANNED — no task in this document is implemented yet.** Every row below is ⬜.
> This plan turns [`cnaplatform.md`](cnaplatform.md) into an executable task list.
>
> **Goal:** separate CNA from SDL3. Today SDL3 is called directly from the runtime, the input
> stack, audio, media, devices, storage, content and 40-odd renderers. After this plan, all of
> that goes through a CNA-owned platform contract (`CNA::Platform::IPlatform` and friends), and
> **SDL3 becomes the first implementation of that contract, not the substrate CNA is written
> against.**
>
> **Explicit scope boundary:** this plan implements **exactly one** platform implementation —
> `Sdl3Platform`. **SDL2, SDL 1.2, a native Win32 platform and any other implementation are NOT
> implemented here.** They appear only in [§12 Possible future implementations](#12-possible-future-implementations-not-in-scope)
> as the reason the seam is shaped the way it is. No task in Phases 0–11 may be closed by adding
> a second SDL implementation.
>
> **Status legend:** ✅ implemented *and verified against its stated acceptance criteria*;
> 🟨 code or documentation exists but has not met those criteria; ⬜ not implemented;
> ⛔ not implementable yet, with the blocking task and the reason named in the row — distinct
> from ⬜ because the work is understood and waiting, not merely undone;
> ❌ cut, with the evidence that killed it recorded in the row.

---

## 1. Why this plan exists

CNA's public API is XNA 4.0. XNA 4.0 says nothing about SDL. SDL3 is an implementation detail
that has leaked into essentially every subsystem, which costs the project three things:

1. **Portability.** Any target where SDL3 is impractical (older Windows, older Linux
   distributions, embedded or historical systems) is unreachable, no matter how portable the
   renderer for that target is. `DIRECTX1`…`DIRECTX8`, `GDI` and `GLIDE` exist precisely to reach
   old systems, and every one of them currently obtains its `HWND` from SDL3.
2. **Testability.** Subsystems could not be exercised without SDL3 being initialized, which is why
   several test suites carried hand-rolled `FakeSdl*Backend` doubles. The migration replaces those
   ad-hoc seams with shared canned implementations of CNA's platform contract; PLAT-82, for example,
   deleted `FakeSdlGamepadBackend` after moving its deterministic coverage to `CannedGamepad`.
3. **Contract clarity.** `IGraphicsRenderer.hpp` originally carried three `// TODO: SDL dependency
   should be abstracted later` methods on its *public internal contract*, plus an `SDL_Window*`
   creation field. PLAT-59/60 removed all three methods; only the creation and registry window
   types remain for PLAT-58/61.

The design rule from `cnaplatform.md` is binding on every task here:

> Do not start from an abstraction based on what SDL1, SDL2 and SDL3 have in common. Start from
> the contract CNA needs, and let each SDL implement that contract to the best of its ability.

## 3. Design decisions (recorded before implementation, not left implicit)

1. **New module `modules/platform` (`cna_platform`).** The contract and the SDL3 implementation
   are one physical module, following `docs/physical-modules.md`: contract headers under
   `modules/platform/include/CNA/Platform/`, the SDL3 implementation under
   `modules/platform/src/Sdl3/`. A separate module per implementation is deferred until a second
   implementation actually exists — inventing `modules/platform-sdl3` now would be a physical
   split with exactly one occupant.

2. **`CNA::Platform`, not `Microsoft::Xna::*`.** None of this is XNA 4.0 API. It never appears in
   a `Microsoft::Xna::Framework` header, and it therefore never needs `CNAEXT` — `CNAEXT` marks
   non-XNA surface *inside* the XNA namespace. Where a platform type must be reachable from an
   XNA type (e.g. `GameWindow`), the XNA-side accessor is `CNAEXT`-tagged as usual.

3. **Compile-time selection, runtime polymorphism.** `CNA_PLATFORM` is a CMake cache variable
   with values `SDL3` (default) and `HEADLESS`; `SDL2` / `SDL12` / `WIN32` are *reserved
   identifiers only* and configuring with them is a hard CMake error naming this plan. Only the
   selected implementation is compiled. `IPlatform` stays virtual anyway, because `HEADLESS` and
   the conformance suite need two implementations in one binary; the `using ActivePlatform = …`
   devirtualization sketched in `cnaplatform.md` is explicitly **not** adopted — it buys a
   sub-0.3 % win the performance contract already says is irrelevant, at the cost of making the
   conformance suite impossible.

4. **Coarse-grained by construction.** The performance contract from `cnaplatform.md` §"Recommended
   performance contract" is a *review rule*, enforced by PLAT-9's lint: no platform call may
   appear inside a per-pixel, per-vertex, per-fragment, per-sample or per-event loop. Events are
   polled as a batch (`PollEvents(std::vector<PlatformEvent>&)`), audio is filled a buffer at a
   time, input is a per-frame snapshot, capabilities are read once and cached.

5. **The graphics layer never calls through the platform to draw.** Renderers receive a
   `NativeWindowHandle` (plus size/DPI/lifecycle notifications) at initialization and then talk to
   their own API directly. `Game → GraphicsDevice → Platform → SDL → Renderer` is forbidden; the
   chain stays `Game → GraphicsDevice → Renderer`.

6. **Four renderers are permitted to keep a hard SDL3 dependency**, in two distinct kinds
   (established by PLAT-3's audit, which corrected this decision's original count of three):
   - *SDL by identity* — `SDL_RENDERER` and `SDL_GPU`. Their rendering path **is** an SDL3 API.
   - *SDL by upstream dependency* — `FNA3D` and `FREEDIRECT`. CNA's own sources for these are
     effectively SDL-free already; the third-party library each wraps links SDL3 itself, and
     free-direct creates and owns an internal `SDL_Renderer` that CNA never sees. No amount of
     migrating CNA code removes this, which is why it is a separate kind of exception rather
     than the same one.

   All four are declared `REQUIRES_PLATFORM SDL3` in CMake and excluded from the
   no-SDL-outside-platform gate by an explicit allowlist, not by accident. Every other renderer
   must end this plan SDL-free.

7. **Audio is a separate contract from platform.** `CNA::Audio::Platform::IAudioDevice` lives in
   `modules/audio`, is selected by its own `CNA_AUDIO_PLATFORM` variable, and does not inherit
   from `IPlatform`. This is what allows a future OpenAL/WASAPI/ALSA backend to exist without a
   matching window/event implementation, exactly as `cnaplatform.md` §"Separate audio out on its
   own" argues.

8. **Gamepad is part of the platform input contract, not its own module.** `cnaplatform.md`
   floats a separate gamepad module because SDL1 joystick, SDL2 GameController and SDL3 Gamepad
   differ so much. That difference is real, but it is a *capability* difference, and the
   capability model already expresses it. A separate module would be justified only once a
   second implementation demonstrates the seam is wrong — noted as a future revisit in §12.

9. **Migration is strangler-style, never big-bang.** Each subsystem moves behind the contract in
   its own task with its own build+test verification. `Sdl3Platform` is introduced *first* and
   proven behaviorally equivalent (Phase 3's golden tests) *before* any subsystem is rewritten to
   depend on it. At no point in this plan is the repository left unbuildable between tasks.

10. **The gate ratchets, it does not flip.** PLAT-8 lands a counter of SDL references outside the
    allowlisted locations, wired into the build as a *warning with a recorded maximum*. Each
    migration task lowers the recorded maximum. PLAT-121 flips it to a hard error once the count
    reaches the allowlist floor. This makes regressions visible from day one instead of at the end.

## 5. Non-negotiable rules

1. **No SDL type in any contract header.** `NativeWindowHandle` carries `void*`, never
   `SDL_Window*`. A forward declaration `struct SDL_Window;` in a CNA header is exactly the
   pattern being removed — `GameWindow.hpp`, `GraphicsDeviceManager.hpp` and
   `IGraphicsRenderer.hpp` all currently do this.
2. **No behavior change is a goal of this plan.** Every migration task's acceptance criterion is
   *identical observable behavior*, proven by the existing test suite plus the golden tests from
   Phase 3. A behavioral fix discovered on the way gets its own commit and its own note.
3. **Unsupported means refused, not silently ignored.** A capability that an implementation lacks
   throws or returns a documented failure. Silent no-ops are forbidden — the same rule the SKIA
   and HEADLESS renderer plans already enforce.
4. **Capabilities are read once.** `GetCapabilities()` returns by value and callers cache it in
   the owning subsystem (`GraphicsDeviceManager`, `GameWindow`, `InputManager`). Calling it
   per-frame is a review rejection.
5. **The 46 renderer identities keep working throughout.** No task may reduce renderer coverage.
   Every renderer migration task names the exact renderer(s) it touches and rebuilds them.
6. **One task = one commit**, per `CLAUDE.md`. Task IDs (`PLAT-n`) go in commit messages.

| PLAT-9 | Hot-path lint for platform calls | ✅ | `tools/platform/hot_path_lint.py` + `cmake/PlatformHotPathLint.cmake`, included from the root `CMakeLists.txt`. **Currently zero violations across 1243 production sources**, and a **hard error** rather than a warning like the ratchet — the ratchet warns because the whole tree is over budget by design and failing would block every task, whereas this one starts at zero and every regression is a single deliberate line with an obvious fix. Warning would mean the count only ever goes up. A violation needs **two independent judgements**: (a) *it is a platform call* — the 98 method names are read out of the contract headers themselves, so a method added to `IPlatform` tomorrow is covered without touching the script, and the call must additionally be reached through a **platform receiver** (a variable whose declaration names a platform interface type, or an ambient accessor) because a bare name match on `Update`/`GetName`/`Clear` would be unusable; (b) *it is inside a hot loop* — a `for`/`while` whose header names a hot token. **`frame` is deliberately absent from that token list**: the game loop is per-frame and a platform call there is correct, so flagging it would train everyone to suppress the tool. Verified against a four-case probe (per-pixel nested loop → caught; per-frame loop → correctly silent; annotated → silent; bare marker → rejected), then removed. |

Headers and types only. No SDL3 code, no migrations. Every header in this phase must compile
against a translation unit that has never seen an SDL header — that is the phase's exit test.

## Phase 10 — `TerminalPlatform` (optional, gated on Phase 8)

Feasibility established in [`docs/platform-terminal-analysis.md`](docs/platform-terminal-analysis.md).
**Verdict: yes for output and mouse, qualified for keyboard, no for gamepad** — and no new renderer
is needed, because a terminal is another consumer of `IPlatformSurfacePresenter` (PLAT-127).

Why it belongs in this plan rather than §12: it is the strongest available proof that the contract
is not SDL-shaped. `HeadlessPlatform` implements every method by doing nothing, so a contract built
entirely around SDL3's assumptions would still pass it. A terminal has a real output device with a
different model (cells, not pixels), real input with a different model (byte streams, not key
state), and a capability profile that is mostly `false`. If the contract survives it, it is real.

**Sequencing is deliberate: this phase runs *after* Phase 8, never before.** Written before the
contract has been proven against `Sdl3Platform` and the conformance suite, a terminal
implementation would shape the contract around terminal quirks — the mirror image of the
SDL3-shaped mistake this whole plan exists to avoid.

| PLAT-129 | Terminal capability spike | ✅ | `terminal-spike/` (source + README committed, binaries gitignored, per `CLAUDE.md`'s spike convention). Measured end to end through `GetLastRedrawnCellCount()`: a still picture costs **0 cells** after its first frame, and a one-cell change costs one cell and under a tenth of a full frame's bytes. |
| PLAT-134 | Colour degradation ladder | ✅ | Landed with PLAT-132 rather than after it, deliberately: the encoding is a single `switch` in `TerminalAnsiWriter`, and leaving two of its four arms unimplemented would have been exactly the silent no-op the capability model forbids — a terminal on the 256-colour rung would have received nothing. All four rungs are implemented and tested, and PLAT-129's detection chooses between them when the presenter is created. Two details found by writing it: the 256-colour rung must prefer the **24-step grey ramp** at 232–255 over the 6×6×6 cube's six-step grey diagonal for near-grey colours, or a greyscale picture comes out visibly tinted; and the monochrome rung emits **no colour escape at all** rather than a black one, because a terminal without colour renders the parameters as literal text. `AsciiQuantizeMode`'s `Color`/`BlackWhite` was not reused — see PLAT-132 for the dependency cycle that rules it out. |
| PLAT-135 | Frame budget | ✅ | `TerminalFrameBudget`, a token bucket the presenter consults before each write. The row's reasoning holds and sharpens: the write **blocks**, so a frame the terminal cannot take does not merely arrive late — it drags the game's own frame rate down with it. Dropping is the honest failure. **The rate is measured, not configured, so there is no constant here to get wrong.** A write that returns at once means the terminal kept up; a write that blocks means it did not, and how long it blocked *is* the link's throughput. The budget refills at the rate it last achieved, smoothed, so a local pseudo-terminal never has the budget bind while a bad ssh link is throttled within a few frames. Three details. **(1) Dropping is safe only because of PLAT-133.** The presenter leaves its record of what is on screen untouched when it drops, so the next affordable frame's diff covers everything that changed since the last frame *actually drawn* — not merely since the dropped one. Without damage tracking this would leave the screen permanently stale. **(2) A full redraw is exempt.** It happens on the first frame and after a resize, where the screen is *wrong* rather than stale; dropping it would leave the terminal blank, or showing the previous size's picture, until something else forced a redraw. **(3) Unspent budget is capped at one second.** Otherwise a program that paused for a minute would be allowed a minute of output in one frame — exactly the blocking write this exists to prevent. Smoothing is tested from both sides: one slow write must not convince it the link collapsed, and a link that really degraded must be believed within a handful of frames. `GetDroppedFrameCount()` is public because a caller seeing a low frame rate deserves to know whether the terminal or the game is the reason. |
| PLAT-136 | Terminal window + `SIGWINCH` | ✅ | `TerminalResizeWatcher` plus the poll-time conversion in `TerminalPlatform::PollEvents`. A resize becomes `WindowEventKind::Resized` **and** `PixelSizeChanged` — both, because a caller resizing its backbuffer watches one while a caller laying out a UI watches the other, and emitting only one silently breaks whichever half of a game listened for the other. There is no display scaling here, so the two always carry the same size. Four points. **(1) The handler sets a flag and nothing else.** `SIGWINCH` carries no size, so the size is read at poll time — which also makes coalescing free and correct: ten resizes between two frames have one current size, and a queue would deliver nine events describing sizes that no longer exist. **(2) One deviation from the row as written.** The row said client bounds should *be* the cell grid; instead the requested size stands at creation and the terminal becomes authoritative only when it changes. Overriding at creation would break `PlatformWindowConformance.WindowReportsItsRequestedTitleAndSize`, and PLAT-141 is the row that pays for this phase — a conformance assertion is not something to bend for one implementation. The resulting behaviour is also what a real windowing system does when a window manager resizes a window after it was made. **(3) A terminal resize is applied at once, not on `Sync()`**, because `SetSize()` is a caller's *request* while this is the display stating a fact; a window still reporting the old size would contradict the event it just delivered. **(4) The watcher is installed only when a window exists** — a process-global signal handler is state a constructor has no business changing, and the conformance suite constructs platforms in processes whose dispositions belong to somebody else. Cell size is a nominal 8×16, chosen for its 1:2 ratio; the absolute numbers do not matter but the ratio does. Tested end to end by `tools/platform/terminal_resize_harness.cpp` under a real pseudo-terminal, because in CI this process has no terminal and the two assertions that matter most would otherwise skip — the same defect this campaign already found once in `PlatformWindowConformance`. |
| PLAT-137 | Keyboard: Kitty protocol path | ✅ | `TerminalKeyboard` + the shared `TerminalInputDecoder` implement canonical Kitty `CSI ... u` input with flags **15** (disambiguation, event types, alternate keys, every key as CSI-u). Press/repeat/release update one held-key snapshot exactly; repeats never duplicate a key, and physical identity is retained so releasing main Enter while keypad Enter is held does not clear `KeyCode::Enter`. The decoder maps ASCII/OEM, F1–F24, editing, modifier, media and keypad PUA codes, preserves base-layout identity as the HID `Scancode`, carries CNA `KeyModifier` bits, buffers split reads and bounds malformed input. `PollEvents()` and `IPlatformKeyboard::Update()` share the same decoder, so neither can steal bytes from the other. `TerminalSessionController` is the lifecycle decision PLAT-137/139 needed: dormant at construction, RAII leases merge presenter/keyboard/mouse modes into the process's one signal-safe `TerminalSession`, rebuild on a changed union, and force a presenter's next frame to be complete when alternate-screen contents were invalidated. Kitty mode is pushed with `CSI > 15 u` on the correct main/alternate-screen stack and popped with `CSI < u` before leaving that screen; the spawned restoration harness now asserts that pop on normal return, SIGINT/SIGTERM/SIGHUP/SIGABRT and uncaught exception, with `_exit()` still proving the test can fail. `TerminalPlatform` probes lazily and reports `exactKeyboardState = true` only when Kitty answered; PLAT-138 supplies the inexact branch on the same service. The expanded keyboard suite also caught and fixed an exact-path mapping defect: HID leaves a numeric gap between F12 and F13, so F13–F24 need their own scancode range rather than arithmetic from F1. Verified in SDL3, Headless and Terminal selections. |
| PLAT-138 | Keyboard: synthetic key-up fallback | ✅ | The shared `TerminalInputDecoder` now has a traditional terminal mode for printable ASCII (including shifted OEM keys), control chords, Alt prefixes, SS3 F1–F4 and xterm CSI navigation/editing/F1–F20 with `;N` modifiers. A first byte emits a fresh press and enters the held snapshot; another matching byte is a repeat and refreshes a **100 ms** deadline; expiry emits exactly one release and removes the key. A separate **30 ms** Escape deadline lets split CSI/SS3 sequences win without making the Escape key disappear. Modifier bits participate in the synthetic snapshot even though a legacy terminal cannot report modifier keys independently. The timeout deliberately sits past common repeat intervals: shortening it creates releases between repeats, while lengthening it leaves taps held longer; the initial OS repeat delay can therefore still produce a held-key stutter, an ambiguity the byte stream cannot resolve. `TerminalPlatform` exposes this keyboard whenever both terminal descriptors are usable but keeps `exactKeyboardState = false`, distinguishing service presence from this quality flag as the contract requires. The fallback acquires the same raw-mode session lease as the exact path but never pushes or pops Kitty state. The 17-test keyboard suite (11 pty-backed) covers decoding, fresh/repeat/release timing, modifier lifetime, split Escape, session restoration and both capability branches; the terminal/session/conformance matrix passes in SDL3, Headless and Terminal configurations. |
| PLAT-139 | Mouse via SGR 1006 | ✅ | `TerminalMouse` and the shared `TerminalInputDecoder` implement xterm SGR-1006 press, release, all-motion and vertical/horizontal wheel reports. Mouse and keyboard deliberately share one descriptor reader and one ordered `PlatformEvent` queue, so polling either service cannot steal or reorder the other's bytes. A mouse lease enables `1000` button, `1003` all-motion and `1006` SGR modes only while input is consumed; the existing signal-safe session epilogue disables the exact inverse set. One-based terminal cells become nominal client coordinates at **8×16** per cell, matching the resize/presenter convention, with checked saturation for hostile coordinates; snapshots retain held-button and accumulated-wheel state. The service exists on a queryable TTY while `pixelAccurateMouse` deliberately remains false because SGR-1006 reports cells, not pixels. Pointer warp, visibility, shape, relative mode, capture and global-position operations refuse deterministically instead of pretending. Six pty-backed tests cover decoding/malformed input, state/events, session modes, ordered Kitty+mouse input, refusals and platform wiring. Focused terminal/session/conformance matrices pass in SDL3 (**115 passed / 2 skipped**), Headless and Terminal (**98 passed / 1 skipped** each), and the registered platform ctests include the new suite. |
| PLAT-140 | Terminal capability profile + refusals | ✅ | The final profile is explicit and tested: there is no gamepad, haptic or sensor service through a TTY, their capability bits remain false, their accessors return null, and the selected-terminal `GamePad::GetState()` control reports disconnected. Terminal windows now return their own `NativeWindowSystem::Terminal` discriminator with every pointer/id null; `HasNativeWindow()` rejects it and diagnostics say `Terminal` rather than misleadingly calling it `Headless`. CMake rejects a `TERMINAL` platform paired with any renderer except the six CPU choices (`SOFTWARE`, `SKIA`, `BLEND2D`, `PORTABLEGL`, `HEADLESS`, `STUB`) **before renderer dependency probing**, so `TERMINAL+VULKAN` for example names the incompatibility and allowed set instead of requesting an SDK or reaching a null handle. PLAT-53's default logger sink was pinned to stderr, and the one `GraphicsDevice` startup diagnostic that still bypassed it via `std::cout` now uses `Logger`; an end-to-end construction test captures both descriptors and proves stdout stays empty. The already-live presenter refusal remains the redirected-output boundary: `surfacePresentation=false` and `CreateSurfacePresenter()` throws `PlatformNotSupportedException(SurfacePresentation)` when stdout is not a TTY, so no escape bytes enter a pipe/file/CI log. Focused profile/native-handle/logger/conformance matrices pass in SDL3 (**94 passed / 2 skipped**), Headless and Terminal (**77 passed / 1 skipped** each); skips require a real terminal or SDL video device. |
| PLAT-141 | Run the conformance suite against `TerminalPlatform` | ✅ | PLAT-116's complete implementation-neutral suite is instantiated from `PlatformFactory::GetAvailable()` rather than a hand-maintained implementation list. `--gtest_list_tests` mechanically confirms all 25 cases (18 general + 7 window) for `Terminal` as well as `SDL3` and `Headless`: the default build runs 75 instances with **74 passed / 1 applicable SDL3 skip**, while both the HEADLESS-selected and TERMINAL-selected builds run their available Headless + Terminal implementations **50/50 passed**. The two registered ctest entries, `CnaPlatformTests` and `CnaPlatformWindowTests`, also pass. This is the row that pays for the whole phase: a third implementation with a radically different capability profile passes the same contract without Terminal-specific branches in the suite, demonstrating that the abstraction is genuinely implementation-neutral rather than SDL3 with extra steps. |

## 10. Risks

| Risk | Mitigation |
|---|---|
| Event-semantics drift between implementations | PLAT-6 captures the oracle *before* any change; PLAT-118 enforces it cross-implementation. |
| Native handle interop bugs (X11 `Window` is an integer, not a pointer) | PLAT-13's per-system documentation table + PLAT-14's validating typed accessors. |
| Two parallel abstractions in `modules/input` | PLAT-77 maps the existing seam onto the new one *before* any migration; PLAT-90 deletes what is superseded. |
| Duplicate clipboard/power surfaces in `input` and `devices-ext` | PLAT-88/89 and PLAT-100/101 are explicitly paired to share one service. |
| SDL subsystem init/quit ordering regressions | PLAT-4 audits it first; PLAT-29 preserves it; existing ordering tests are the gate. |
| Renderer coverage silently shrinking | Rule 5; every Phase 4 task names the renderers it touches and rebuilds them. |
| Performance regression in the fixed-timestep loop | PLAT-7/PLAT-39/PLAT-120; batch events, snapshot input, cached capabilities. |
| The plan stalls half-migrated | The PLAT-8 ratchet makes partial progress visible and prevents backsliding at any point. |

## 11. Definition of done

This plan is complete when **all** of the following hold:

1. No production source outside `modules/platform/src/Sdl3/`, the SDL3 audio implementation, and
   the four allowlisted renderers includes an SDL header — enforced by PLAT-121, not by review,
   with `renderer_sdl_audit.py --check` covering the renderer half.
2. No SDL type appears in any CNA header, including forward declarations.
3. All 46 renderer identities still build and pass their existing tests.
4. The full test suite passes under `CNA_PLATFORM=SDL3`.
5. The display-independent test suite passes under `CNA_PLATFORM=HEADLESS` with no display server.
6. The conformance suite passes against all three implementations: SDL3, Headless and Terminal.
7. Performance shows no regression outside PLAT-7's measured noise floor.
8. `docs/platform-abstraction.md` documents the contract well enough that a second implementation
   could be written from it without reading `Sdl3Platform`'s source.

## 12. Possible future implementations (NOT in scope)

**None of the following is implemented by this plan.** They are recorded because they are the
reason the contract is shaped as it is — a contract designed for exactly one implementation would
have come out SDL3-shaped, which is the failure mode `cnaplatform.md` warns against. Each would
need its own plan file.

| Candidate | Rationale | Expected capability profile | Status |
|---|---|---|---|
| `Sdl2Platform` | Older Windows (back to XP per SDL2's docs), older Linux distributions, targets where SDL3 is impractical, and a long-term fallback path. The most realistic second implementation. | Close to full, minus the SDL3 GPU API; gamepad and HiDPI contracts differ. | Future — not started |
| `Sdl12Platform` | Genuinely historical systems. SDL 1.2 is deprecated upstream (last release 1.2.15) and would be CNA-owned indefinitely. | Limited profile: basic window, keyboard/mouse, old joystick API, timing, basic audio, GL or software surface, basic fullscreen. Clipboard, text input, gamepad, HiDPI largely unsupported — declared unsupported, never emulated with unsafe hacks. | Future — not started |
| `Win32Platform` | A native platform with no SDL at all, pairing naturally with the `GDI` and `DIRECTX*` renderers. | Windows-only; no cross-platform pretence. | Future — not started |
| `EmscriptenPlatform` | A direct browser platform for the web renderers. | Web-shaped: no multiple windows, no native dialogs. | Future — not started |
| `TerminalPlatform` | Runs a game in a TTY — over SSH, in CI, in `tmux`, on any machine with no display server. **Not listed here as future work: it was analysed and promoted to Phase 10**, because it is the strongest available proof the contract is not SDL-shaped. | Cells not pixels; mouse at cell granularity; exact keyboard only under the Kitty protocol; no gamepad. | **Analysed — Phase 10** |
| Separate gamepad module | If a second implementation shows the capability model cannot express the SDL1-joystick vs SDL2-GameController vs SDL3-Gamepad gap (design decision 8), the gamepad seam is split out then — on evidence, not in advance. | — | Future — revisit after a second implementation exists |
| Audio implementations (OpenAL, WASAPI, ALSA) | The audio contract (Phase 6) is separate precisely so these need no matching platform implementation. | — | Future — not started |
| `sdl2-compat` / `sdl12-compat` as test configurations | Useful to shake out API-generation assumptions, but they run on SDL3/SDL2 underneath and therefore reach **no** new operating system. They are a test configuration, never a substitute for a real implementation. | — | Future — not started |
| Legacy C++/toolchain profile | Separating SDL3 is necessary but **not sufficient** for genuinely old targets: an older compiler, a language profile below C++23, standard-library restrictions and possibly a C ABI between a modern core and a legacy host are all separate problems. | — | Future — out of scope, own plan required |

The ordering `cnaplatform.md` recommends, for whenever that work starts: prove SDL3 equivalence
first (Phases 0–9 here), then add `Sdl2Platform`, then extend the conformance suite, then design a
limited `Sdl12Platform`, and only last address the legacy C++/toolchain profile.
